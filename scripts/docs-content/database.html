Database

Shepherd keeps everything in PostgreSQL — pipelines, organisations, credentials, sessions — and holds no state of its own. That makes the database the one thing worth backing up, and Shepherd itself something you can delete and reinstall freely.

You have two ways to give it one, and both are fully supported.

Bring your own

The default. Point SHEPHERD_DATABASE_URL at an RDS, a Cloud SQL, an Azure Database, or a Postgres you already run, and put it in the secret the chart reads:

shell
kubectl -n shepherd create secret generic shepherd-secrets \
  --from-literal=SHEPHERD_DATABASE_URL='postgres://user:pass@my-rds.eu-west-1.rds.amazonaws.com:5432/shepherd?sslmode=require' \
  --from-literal=SHEPHERD_SECURITY_ENCRYPTION_KEY="$(openssl rand -base64 32)"

helm install shepherd oci://ghcr.io/procoduck/charts/shepherd --version 0.9.0 \
  --namespace shepherd --set existingSecret=shepherd-secrets

Shepherd needs an ordinary database and an ordinary role that owns it. No superuser, no extensions beyond what a stock PostgreSQL 14+ ships, and no manual schema step — migrations run themselves on install and upgrade.

Let the chart provision one

If you would rather not run a database by hand, CloudNativePG can run it in the same cluster. Install the operator once, then:

shell
helm install shepherd oci://ghcr.io/procoduck/charts/shepherd --version 0.9.0 \
  --namespace shepherd \
  --set cnpg.enabled=true \
  --set existingSecret=shepherd-secrets   # still holds the encryption key

The chart renders a postgresql.cnpg.io/v1 Cluster and wires Shepherd’s database URL to the uri key of the <cluster>-app Secret the operator generates. You never write a connection string, and SHEPHERD_DATABASE_URL is not needed in your secret at all.

The chart does not install the operator. CloudNativePG and its CRDs must already be in the cluster, exactly as with the Gateway API for route.enabled. Without them the install fails with no matches for kind Cluster.

Three things worth knowing

  • The Cluster is created before the migration Job, as a Helm pre-install hook, because the migration has nothing to talk to otherwise.
  • First install takes a few minutes and the migration Job may fail a few times first. Postgres is still initialising while the Job is already running; the Job retries with backoff (migrations.job.backoffLimit) until it connects. Failed attempts in the log during a first install are expected, not a fault.
  • helm uninstall does not delete the database. Hook resources are not tracked in the release, which for the thing holding all your data is the right way round. Remove it deliberately: kubectl -n shepherd delete cluster shepherd-db.

Sizing it

values.yaml
cnpg:
  enabled: true
  instances: 3                 # a primary and two standbys
  storage:
    size: 20Gi
    storageClass: fast-ssd
  resources:
    requests: { cpu: 500m, memory: 1Gi }
  # Anything the chart does not surface goes here verbatim: backups,
  # monitoring, affinity, postgresql.parameters.
  extraSpec:
    backup:
      barmanObjectStore:
        destinationPath: s3://my-backups/shepherd

Every key is listed in Helm values. Backup, restore and failover are the operator’s job, not Shepherd’s — see the CloudNativePG documentation.

This path is tested against a real operator, not just rendered: Shepherd’s Kubernetes suite installs CloudNativePG into a throwaway cluster on every change to the chart, installs Shepherd with nothing supplied, and asserts the database is provisioned and the migrations actually reached it.
