Authoring pipelines

A pipeline is a fragment of Alloy config plus the matchers that decide which collectors receive it. Shepherd merges every enabled pipeline whose matchers select a given collector into the single config that collector is served. There are three ways in, and they all land in the same merge engine.

1. A wizard, if your job is a common one

Six guided forms cover the jobs most fleets need. Answer the questions, preview the Alloy it generates, commit it as a pipeline. A wizard writes to one of your org’s destinations, and gets that destination’s URL and authentication.

Database Metrics never sees the database password. By default it asks for a Kubernetes Secret’s namespace, name and key, and each collector reads the value itself through remote.kubernetes.secret, the same way a destination’s credentials are read. For PostgreSQL and MySQL the key (default dsn) holds the whole connection string — postgresql://user:password@host:5432/db?sslmode=require, or user:password@tcp(host:3306)/; for Redis the address is a plain answer and the key (default password) holds the password — if the Secret lacks that key, the collector still loads and connects to Redis without a password. The Secret must exist on every cluster the pipeline matches, and the collector needs get on Secrets in the Secret’s namespace. If a collector cannot read the Secret, or the value is not a valid DSN, it refuses its whole config, so create the Secret before you commit.

The Secret source is for collectors running in Kubernetes. A collector on a host or VM cannot read a Kubernetes Secret and refuses its whole config, so keep the pipeline’s matchers to Kubernetes clusters. For other collectors choose the env credential source, which reads an environment variable that you must set on those collectors yourself — Shepherd does not set it.

2. The visual builder, when you want to see the graph

Drag components from the palette onto the canvas and wire their ports together. The Generated config tab shows the Alloy it produces as you work, and the validity chip in the toolbar goes red the moment the graph would not run — you cannot save a broken one.

The graph below generates the config beside it. This is the same Alloy that will be merged and served — there is no separate translation step to be surprised by.

3. Raw Alloy, when you already know what you want

Paste the config. It goes through exactly the same gate as the other two.

4. Revisions and restore

Every save is a numbered revision. The editor can show any past revision as a diff against the current text, so you can see exactly what changed and who changed it.

Restoring a revision does not rewrite history — it creates a new revision from the old one's contents, matchers and enabled state — so restoring a revision saved while the pipeline was disabled disables it, and the dialog says so — and runs it through the same validation gate as any other save. A git-managed pipeline can be restored too, but the next sync from the repository wins.

All three land in the same place. A wizard and the visual builder are editors, not separate systems — each produces Alloy config that goes through the same validation gate and the same merge engine as config you paste by hand. There is no translation step to be surprised by later.
