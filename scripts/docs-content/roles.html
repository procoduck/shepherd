Roles and access

A person’s role reaches Shepherd two ways, and the two coexist. Either your identity provider puts them in a group Shepherd knows about, or an application administrator gives them a local account and a role in an organisation. Neither is a fallback for the other — you can run entirely on single sign-on, entirely on local accounts, or mix them, and a session is judged on one source only.

The roles

ActorCanCannot
Application administrator Everything, everywhere: create organisations and set their tenant identity, claim clusters into orgs, issue and revoke agent tokens, configure single sign-on, manage local accounts. —
Organisation administrator Everything inside one org, including what the org is: destinations, tenant routes, git credentials and repo links, teams, service accounts, and the group assignments on that org’s collectors. Reach another org, claim clusters, or manage agent tokens.
Organisation editor Author what the org runs: pipelines, wizards, the visual builder, simulations. Change where telemetry ships — destinations, tenant routes, git credentials and teams stay with the org admin.
Team member Write the pipelines their team owns — scoped write, with no wider access. Touch pipelines their team does not own.
Viewer View collectors they are assigned to, and the pipelines and served config affecting them. Create or change anything.
Service account (apply) Machine writes within one org, and every write must name the human it acts for — a claim verified against the credential, not taken on trust. Ever be an app admin. Act without an on-behalf-of.
Service account (propose) Read, validate and simulate freely. Apply anything.
Collector (agent token) Fetch its own merged config and report status, over HTTP Basic auth. Read or change anything in the management API.

Why there is an editor tier

Writing a pipeline and re-pointing where an org’s telemetry ships used to be the same permission: both needed org admin. They are different risks. An editor can author freely without being able to change a destination, a tenant route, or a git credential — so the person who tunes a scrape interval does not also hold the ability to redirect the fleet’s data somewhere else.

How a role is assigned

From your identity provider. Each organisation names an admin, editor and reader group at Admin → Orgs. Whatever your provider emits in the groups claim is matched against those values — object GUIDs for Microsoft Entra, and for every other provider whatever it actually emits, usually a group name or a path. App-admin rights come from auth.app_admin_group_ids.

From a local account. An app admin creates the account at Admin → Users and assigns its role per organisation there. See Users and teams.

An account with no organisation sees nothing. It can sign in, and that is all. Assigning at least one org role is part of creating a usable account, not a separate administrative step.
