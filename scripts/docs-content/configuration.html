Configuration

Shepherd reads its settings from a YAML file and from SHEPHERD_* environment variables, which override it. In a chart install the non-secret settings come from the chart’s config: block, rendered into a ConfigMap mounted at /etc/shepherd/shepherd.yaml, and the secrets below from a Kubernetes Secret; in local development, from your shell (and ./shepherd.yaml if present). Only two settings are required — the server refuses to start without them — and the rest matter only for the setups they name.

The secret Shepherd reads

In a chart install these are keys of the Kubernetes Secret the chart reads (shepherd-secrets by default, or override existingSecret). Running locally, they are plain environment variables.

KeyRequired?Description
SHEPHERD_DATABASE_URLYesPostgreSQL connection string
SHEPHERD_SECURITY_ENCRYPTION_KEYYesBase64-encoded 32-byte key encrypting stored credentials at rest. Keep it — a replacement key cannot decrypt what the old one wrote
SHEPHERD_BOOTSTRAP_ADMIN_PASSWORDRecommendedPassword for the administrator created on first boot. Read only while the users table is empty. Leave it unset and the account is created as admin/admin, which can do nothing until the password is changed
SHEPHERD_BOOTSTRAP_ADMIN_LOGINNoLogin of that first administrator; defaults to admin
SHEPHERD_OIDC_CLIENT_SECRETChart-configured SSO onlyOmit it to configure SSO from the UI instead
SHEPHERD_GRAPH_CLIENT_SECRETEntra + Graph lookup onlyNot used by any other provider

See deploy/helm/shepherd/values.yaml for the full set of chart options, including networkPolicy and autoscaling. The chart has no user-seeding options of its own — the bootstrap admin above is the only account a fresh install creates. (shepherd dev seed, which additionally creates local editor/viewer accounts, is a dev-only CLI command outside the chart; see internal/cli/dev.go.)

Where these values come from is a separate decision: see Secrets for supplying them yourself or having them generated, and Database for the connection string.

The encryption key is not rotatable

Keep SHEPHERD_SECURITY_ENCRYPTION_KEY. It encrypts git credentials and the OIDC client secret at rest. A new key on the next boot cannot decrypt what the old one wrote, and Shepherd has no way to tell you which stored secret it has just lost — it simply fails to use them. Generate it once, store it where you store your other secrets, and back it up with them.

The first administrator

SHEPHERD_BOOTSTRAP_ADMIN_LOGIN and SHEPHERD_BOOTSTRAP_ADMIN_PASSWORD are read only while the users table is empty, on first boot. Set the password and the account is yours. Leave it unset and the account is created as admin/admin with a forced password change, which blocks every request except the change itself — so an unattended install cannot quietly sit on a default credential. After first boot, accounts are managed at Admin → Users; see Users and teams.

Client addresses behind an ingress: server.trusted_proxies

Shepherd throttles local sign-in per client address as well as per username. By default it takes that address from the TCP connection and trusts no forwarding header, because any client can send X-Forwarded-For, X-Real-IP or True-Client-IP. Behind an ingress controller or gateway, though, every connection comes from the proxy, so every browser shares one per-IP bucket: about 60 failed sign-ins from anyone, signed in or not, block local sign-in for everyone until they stop. OIDC sign-in is not throttled this way and is unaffected.

server.trusted_proxies (config.server.trusted_proxies in the chart; SHEPHERD_SERVER_TRUSTED_PROXIES, comma-separated) lists the CIDRs your proxies connect from. When a connection comes from one of them, and only then, Shepherd reads X-Forwarded-For right to left, skips entries that are themselves trusted, and uses the first one that is not. Entries a client adds itself sit to the left of what your proxies append, so they are never reached. X-Real-IP and True-Client-IP are never read. Default: empty.

Use the CIDR the proxy pods get their addresses from — usually the cluster's pod CIDR (kubectl get nodes -o jsonpath='{.items[*].spec.podCIDR}', or your CNI's IP pool), since pod addresses change. A bare address is taken as a single host; /0 is rejected. Everything inside the list can claim any client address, so keep it as narrow as your network allows, and add the CIDR of any HTTP load balancer in front of the ingress that appends its own X-Forwarded-For entry.

values.yaml — ingress-nginx
config:
  server:
    # Pod CIDR the ingress-nginx controller pods are scheduled into.
    # ingress-nginx appends the address it saw to X-Forwarded-For.
    trusted_proxies:
      - 10.244.0.0/16
values.yaml — Gateway API (NGINX Gateway Fabric)
config:
  server:
    # Pod CIDR the Gateway's NGINX data-plane pods are scheduled into.
    # NGF appends the address it saw to X-Forwarded-For.
    trusted_proxies:
      - 10.244.0.0/16

Check that the proxy sees real client addresses. If the controller's LoadBalancer Service uses externalTrafficPolicy: Cluster, the address it appends is a node’s, so clients still share buckets per node. Use externalTrafficPolicy: Local (or PROXY protocol) on the proxy’s Service. Get the list wrong in the other direction — a CIDR that does not contain the proxy — and Shepherd simply keeps using the proxy’s address: no spoofing, only the shared bucket.

Single sign-on

One setting decides where SSO configuration comes from: oidc.issuer. Set it in your chart values and the chart owns SSO; leave it unset and an app admin configures a provider from the UI instead. Single sign-on covers both paths and what each one costs you.
