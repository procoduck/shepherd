Destinations

A destination is where an organisation’s telemetry is written: a Prometheus remote-write endpoint (Mimir), a Loki push endpoint, or an OTLP endpoint. Org admins manage them on the Destinations page. Wizards ship to them by name: the destination a wizard step picks becomes that pipeline’s writer (prometheus.remote_write or loki.write), including its authentication.

The URL

Enter the full endpoint URL the collector writes to, for example https://mimir.example.com/api/v1/push or https://loki.example.com/loki/api/v1/push. Shepherd puts it into the writer exactly as written and adds no path.

Authentication from a Kubernetes Secret

Shepherd never holds a telemetry backend’s credentials. For an authenticated destination you name a Kubernetes Secret that already exists on every cluster whose collectors ship there, and the collector reads it at runtime with remote.kubernetes.secret. The served config contains the Secret’s namespace, its name and the key names below, never the values.

Auth modeKeys the Secret must holdWhat the writer gets
None—no auth block
Basic auth (Kubernetes Secret)username, password basic_auth
OAuth2 (Kubernetes Secret) client_id, client_secret, token_url oauth2 (client credentials)

OAuth2 scopes are set on the destination itself (the OAuth2 scopes field, stored as extra.oauth2_scopes), not in the Secret. They are not sensitive, and because Shepherd never reads the Secret it could not tell whether an optional key is there.

Create the Secret in the namespace you name on the destination:

shell
kubectl -n monitoring create secret generic mimir-credentials \
  --from-literal=username=<user> \
  --from-literal=password=<password>

A basic-auth destination named prom-prod pointing at that Secret gives a wizard pipeline this writer:

generated
remote.kubernetes.secret "metrics_auth" {
  namespace = "monitoring"
  name      = "mimir-credentials"
}

prometheus.remote_write "metrics" {
  endpoint {
    name = "prom-prod"
    url  = "https://mimir.example.com/api/v1/push"

    basic_auth {
      username = convert.nonsensitive(remote.kubernetes.secret.metrics_auth.data["username"])
      password = remote.kubernetes.secret.metrics_auth.data["password"]
    }
  }
}

What the collector needs to read the Secret

The collector’s service account needs get on Secrets in the Secret’s namespace: remote.kubernetes.secret reads the one named Secret with a GET when the config loads and again every minute, and never lists or watches. The Grafana Alloy Helm chart, and so k8s-monitoring’s collectors, grants Secret access cluster-wide by default. If your collectors run with narrower RBAC, grant it in that one namespace; the Role below also grants list and watch, which are not needed:

rbac.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: alloy-read-destination-secrets
  namespace: monitoring
rules:
  - apiGroups: [""]
    resources: ["secrets"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: alloy-read-destination-secrets
  namespace: monitoring
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: alloy-read-destination-secrets
subjects:
  - kind: ServiceAccount
    name: <collector service account>
    namespace: <collector namespace>

Shepherd’s Kubernetes test suite runs a real Alloy with exactly this Role and checks that its remote-write requests carry the Secret’s credentials.

When a change takes effect

The writer, auth block included, is generated when a wizard is previewed or committed. It is stored as part of the pipeline, so it passes the same validation as any other line and shows in the editor and its revision history. A wizard that names a destination the organisation does not have, or one of the wrong type, is refused with a message saying which.

Saving a change to a destination regenerates every wizard pipeline in the organisation that ships to it, from the answers stored with the pipeline, in the same step. Each regenerated pipeline passes the full validation gate, gets a new revision and an audit entry under your name, and collectors receive it on their next poll. Renaming a destination renames it in those pipelines too. If any of them would fail validation, nothing is saved and the message names the pipeline, the reason and what to do; each pipeline it names links to its page. The same happens when one of them was edited by hand after its wizard generated it: Shepherd never overwrites the edit. Open the pipeline and do one of three things, then save the destination again:

  • Restore last wizard version drops the hand edit. The pipeline page offers it whenever a wizard pipeline’s text differs from the last revision its wizard wrote; the revision history marks those revisions wizard. It restores that revision as a new one, so the edit stays in the history.
  • Detach from wizard keeps the edit: the pipeline keeps its text, matchers, owner and history, becomes an ordinary pipeline, and no longer follows destination changes.
  • Delete the pipeline.

Running the wizard again does not help: it creates a new pipeline.

Shepherd recognises a hand edit by a fingerprint of the text the wizard last wrote, so a newer version of a wizard does not make older pipelines look edited. A wizard pipeline generated before that fingerprint existed is compared with what its wizard would generate today instead, until its next regeneration records one.

A destination a wizard pipeline still ships to cannot be deleted. The refusal lists the pipelines, each linked to its page; detach them from the wizard, or delete them, first.

Pipelines generated before destination auth

Wizard pipelines committed before destination auth was rendered read their URL from sys.env("SHEPHERD_DEST_<NAME>_URL"), which nothing sets, and carry no auth. Convert them once with shepherd admin rerender-destinations, run with the server's own configuration, --dry-run first:

shell
kubectl exec svc/shepherd -- /usr/local/bin/shepherd admin rerender-destinations \
  --config /etc/shepherd/shepherd.yaml --dry-run

It lists every pipeline it converts and every one it cannot (for example, one naming a destination that was deleted), and is safe to run again. Saving a destination also regenerates the pipelines that use it.
