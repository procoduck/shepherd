GitOps

Instead of authoring in the UI, point Shepherd at a git repository and it will poll for *.alloy files and sync them onto a target collector as pipelines. Any git server works — the credential kinds are personal access token, basic auth, SSH deploy key, an Entra service principal for Azure DevOps, GitHub App installation tokens, and none for a public repository. Set it up under Git sync in the sidebar: add a credential, then a repository link naming the branch, the path and the collector its files are served to.

This page is about Shepherd’s own git sync, not about deploying Shepherd with Argo CD or Flux. If you are looking for the latter, three values matter and each has a default that is unsafe under a tool that renders the chart offline: see cnpg.render, externalSecrets.render, and the sandbox token — the chart generates it at install and looks it up on upgrade, which an offline render cannot do, so every sync would mint a new token and roll both Deployments. Set simulator.token.value or simulator.token.existingSecret (or simulator.enabled=false).

Synced pipelines show git in the Source column and are owned by the repository: they are read-only in Shepherd — the editor will not save them and they cannot be deleted. You can enable or disable one — that sticks — or restore an earlier revision, but the next commit to the repository puts the repository’s text back. A new file becomes an enabled pipeline on its first successful sync; removing a file from the repository does not remove its pipeline. Synced files pass the same three-stage validation gate as everything else, one file at a time: a file that fails is skipped (its previous version keeps being served), the others in the same commit still sync, and the errors are reported on the repo link. Any synced pipeline can be read as a graph.

Git sync is managed by organisation admins.
