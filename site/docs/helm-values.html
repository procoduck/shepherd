Helm values

Every value the chart accepts, generated from values.yaml in chart 0.8.1. The descriptions are the chart’s own comments, so this page cannot describe a value the chart does not have, or miss one it gained.

This page is generated from the chart on main, which can be slightly ahead of the newest published chart. If a value here is missing from the version you installed, check the releases — or run helm show values oci://ghcr.io/procoduck/charts/shepherd --version <yours>, which answers for the exact chart you have.

Only two values are ever required, and neither is here: the database URL and the encryption key live in a Secret, not in values. See Configuration.

cnpg

----------------------------------------------------------------------------- CloudNativePG: let the chart provision the database.
OFF by default, and Shepherd is happy either way — point SHEPHERD_DATABASE_URL at an RDS, a Cloud SQL, or any Postgres you already run and leave this alone. Turn it on and the chart renders a postgresql.cnpg.io/v1 Cluster, and wires Shepherd's database URL to the uri key of the <cluster>-app Secret that CNPG generates. You never write a connection string.
Requires the CloudNativePG operator and its CRDs to be installed in the cluster already; the chart does not install operators.
The Cluster renders as a pre-install/pre-upgrade hook so it exists before the migration Job runs. Three consequences worth knowing: - helm uninstall does NOT delete it. Hook resources are not tracked in the release, which for the thing holding all your data is the right way round. Remove it deliberately with kubectl delete cluster <name>. - Once it exists, changes to cnpg.* no longer reach it: the chart skips rendering a Cluster that is already there, because a hook Helm re-renders is a hook Helm first DELETES. Edit a live cluster with kubectl edit cluster <name>, which is the operator's own interface for it. - On a first install the migration Job may fail a few times while Postgres is still coming up. That is expected and it retries — see migrations.job.backoffLimit.

externalSecrets

----------------------------------------------------------------------------- External Secrets Operator: let the cluster generate the bootstrap secrets.
OFF by default. Enabled, the chart renders two Password generators and an ExternalSecret that produces the Secret Shepherd reads — so the encryption key and the first administrator's password are generated in-cluster and never pass through your shell, your values file, or your terminal history.
Requires the External Secrets Operator and its CRDs; the chart does not install operators. No SecretStore is needed: a generator is the source.
refresh_interval is "0" and MUST stay "0". These are not rotatable credentials: regenerating the encryption key would leave every git credential and OIDC client secret already stored in the database undecryptable, with no error at the moment it happens. deletionPolicy is Retain for the same reason — uninstalling the release must not take the key with it.
Both only hold while the ExternalSecret itself survives, so the chart also skips rendering it once it exists. Changing externalSecrets.* after the first install therefore has no effect; delete the ExternalSecret deliberately if you genuinely want it regenerated, understanding that a new key orphans every credential the old one encrypted.

route

Gateway API HTTPRoute. OFF by default, like ingress below: it needs the Gateway API CRDs, which are not present on a vanilla cluster, so defaulting it on made a plain helm install fail with "no matches for kind HTTPRoute". Templating could never catch that — helm template does not check whether a Kind exists — and every values file in the repo already set it to false, which is how the broken default survived. Enable it deliberately, and set parentRefs/hostnames when you do: an HTTPRoute with neither routes nothing.

metrics

--------------------------------------------------------------------------- Metrics
Shepherd serves Prometheus metrics on a SEPARATE listener from the API (config.server.metrics_listen, default :9090). /metrics on the main port is deliberately 404-guarded, so anything scraping :8080/metrics gets nothing — which is what the ServiceMonitor here used to do.
enabled controls the metrics Service and its container port. It is on by default: the listener runs regardless, and a ClusterIP Service in front of it exposes nothing outside the cluster. Turn it off only if you have a policy against unscraped Services existing. ---------------------------------------------------------------------------

simulator

----------------------------------------------------------------------------- S3 sandbox simulator (VB-1 §6.4) — ENABLED BY DEFAULT since v0.0.1, after both containment gates closed (docs/project-status.md F5: B-CONTAIN-1 fixed and red/green-proven; NetworkPolicy enforcement verified in a real cluster by e2e/k8s/simulator_containment_test.go's probes and kill probe).
TO DISABLE: set simulator.enabled: false below (or --set on install) — nothing simulator-related renders, and shepherd's config is not wired to it. The compose stacks keep their opt-in sim profile: that is test-environment design (the default make e2e deliberately exercises the simulator-absent path), not the product default.
When enabled, shepherd's config is wired to this chart's simulator Service automatically unless you set config.simulator yourself — an explicit config.simulator block always wins verbatim (see templates/configmap.yaml).
It runs USER-AUTHORED Alloy configuration. Every control below is load-bearing, not decoration, and every one is asserted by deploy/helm/chart_test.go so it cannot regress silently: - automountServiceAccountToken: false on its ServiceAccount. Defense in depth, not the only gate — internal/simsvc.Config.SATokenPath makes the binary itself refuse to start if a token is mounted anyway. - a default-deny egress NetworkPolicy. The sandboxed Alloy is a CHILD PROCESS of shepherd-simulator (internal/simsvc/runner.go), not a sibling container, so this Pod's own network boundary IS the sandbox's boundary. Egress is allowed only to this Pod's own harness ports (the capture receivers shepherd-simulator itself serves) and to cluster DNS; nothing else, including the rest of the cluster and the internet. - non-root securityContext, every capability dropped, no privilege escalation, a read-only root filesystem (the run scratch directory is an emptyDir mounted over /tmp). - CPU/memory limits, so one runaway sandboxed config cannot starve the node.
See docs/visual-builder-design-VB1.md §6.4 and docs/archive/reviews/s3-sandbox-security-findings.md (finding H5) for why each of these exists.
