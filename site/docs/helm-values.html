Helm values

Every value the chart accepts, generated from values.yaml in chart 0.10.2. The descriptions are the chart’s own comments, so this page cannot describe a value the chart does not have, or miss one it gained.

This page is generated from the chart on main, which can be slightly ahead of the newest published chart. If a value here is missing from the version you installed, check the releases — or run helm show values oci://ghcr.io/procoduck/charts/shepherd --version <yours>, which answers for the exact chart you have.

Only two values are ever required, and neither is here: the database URL and the encryption key live in a Secret, not in values. See Configuration.

fullnameOverride""fullnameOverride: replaces the whole "<release>-<chart>" prefix, so objects are named exactly this. Empty means the usual release-derived name.

KeyDefaultDescription

service

The Service in front of Shepherd. ClusterIP by default: an Ingress or HTTPRoute (both below) is the intended way in for a real deployment.
type is exposed because the template hardcoded ClusterIP, which left no way to reach Shepherd on a bare cluster without editing the rendered object by hand — kind and other local clusters have no ingress controller, and that is exactly where someone is trying the chart for the first time.

KeyDefaultDescription
service.typeClusterIPtype: the Service's kind (ClusterIP, NodePort, LoadBalancer -- standard Kubernetes values). See above for why this is exposed rather than hardcoded to ClusterIP.
service.port8080port: the container's HTTP port and the port the Service listens on. config.server.listen below must agree with it -- the Deployment's containerPort is hardcoded to 8080, not derived from either value.
service.nodePort""Only used when type is NodePort. Leave empty to let Kubernetes pick one from the node port range.

config

KeyDefaultDescription
config.server.listen":8080"listen: host:port the main HTTP server binds. The Deployment's containerPort and service.port above are both hardcoded to 8080, so changing this alone does not move where the container is reachable -- keep all three in agreement.
config.server.metrics_listen":9090"Metrics listen on their own port; /metrics is never served on listen. The container port, the metrics Service, and the ServiceMonitor are all derived from this value, so changing it here is enough.
config.server.base_url"https://shepherd.example.internal"base_url: Shepherd's own externally-reachable URL, no path. Collectors' remotecfg clients and the beacon's remote-write endpoint are both built against it, so it needs to be an address they can actually reach, not just this Service's in-cluster name.
config.server.beacon_disabledfalseThe beacon (docs/gateway-tier-plan.md D6) serves every claimed collector a small baseline pipeline that reports which components it is running and whether they are healthy — component names only, never config text and never raw samples — and mounts an ingest endpoint at /beacon/v1/write authenticated by the same agent token everything else uses.
It is ON by default and that is deliberate: the collector nobody knows about is exactly the one that would never opt in. Set this to true to turn it off entirely — no endpoint is mounted and no baseline is served. Opting out is offered because the beacon stores inventory and accepts writes, and an operator who cannot answer for that yet should be able to say no without downgrading.

config.log.level"info"level: the minimum log level Shepherd emits, e.g. debug, info, warn, error.
config.log.format"json"format: the log encoding Shepherd writes -- "json" for structured logs (the default, suited to log aggregation) or "text" for human-readable output.

cnpg

----------------------------------------------------------------------------- CloudNativePG: let the chart provision the database.
OFF by default, and Shepherd is happy either way — point SHEPHERD_DATABASE_URL at an RDS, a Cloud SQL, or any Postgres you already run and leave this alone. Turn it on and the chart renders a postgresql.cnpg.io/v1 Cluster, and wires Shepherd's database URL to the uri key of the <cluster>-app Secret that CNPG generates. You never write a connection string.
Requires the CloudNativePG operator and its CRDs to be installed in the cluster already; the chart does not install operators.
The Cluster renders as a pre-install/pre-upgrade hook so it exists before the migration Job runs. Three consequences worth knowing: - helm uninstall does NOT delete it. Hook resources are not tracked in the release, which for the thing holding all your data is the right way round. Remove it deliberately with kubectl delete cluster <name>. - Once it exists, changes to cnpg.* no longer reach it: the chart skips rendering a Cluster that is already there, because a hook Helm re-renders is a hook Helm first DELETES. Edit a live cluster with kubectl edit cluster <name>, which is the operator's own interface for it. - On a first install the migration Job may fail a few times while Postgres is still coming up. That is expected and it retries — see migrations.job.backoffLimit.
GITOPS WARNING. The "skips rendering a Cluster that is already there" trick above uses lookup, which needs a live cluster connection. Argo CD, Flux and helm template | kubectl apply render the chart with no connection, so the guard fails OPEN there: the Cluster is emitted on every sync, and Argo CD in particular treats a pre-install/pre-upgrade hook as a PreSync hook it DELETES before recreating -- which takes the PVCs and the database with it. If you deploy this chart through any such tool, set render: never below once the database exists.

KeyDefaultDescription
cnpg.enabledfalseenabled: turn on to let the chart provision the database via CloudNativePG. See the block comment above for what that means and its GitOps caveat.
cnpg.renderautorender: auto | always | never -- when to emit the Cluster object. auto (default) only when lookup says it is not already there. Correct under the helm CLI; unsafe under GitOps, see above. never never emit it. What a GitOps deployment sets after bootstrap. always emit it unconditionally, for bootstrapping or for a pipeline that wants the full desired state.
cnpg.name""Cluster name. Empty means "<release>-db".
cnpg.instances2Two gives you a primary and one standby, which is the minimum CloudNativePG needs for automated failover. Raise it for more read capacity or headroom.
cnpg.storage.size10Gisize: the PersistentVolumeClaim size for the primary and each standby.
cnpg.storage.storageClass""Empty uses the cluster's default StorageClass.
cnpg.databaseshepherdThe database and the role that owns it. Shepherd needs no superuser.
cnpg.ownershepherdowner: the role that owns database above; Shepherd connects using this role. See the comment above -- no superuser required.
cnpg.imageName""Pinning the image is optional; empty lets the operator choose the version it was built against, which is the one it knows how to upgrade.
cnpg.resources{}resources: CPU/memory requests and limits for the Postgres instances. Empty means unbounded, same as the app's own resources below.
cnpg.extraSpec{}Merged verbatim into the Cluster spec, for anything this chart does not surface: backup, monitoring, affinity, postgresql.parameters, and so on. See the CloudNativePG API reference.

externalSecrets

----------------------------------------------------------------------------- External Secrets Operator: let the cluster generate the bootstrap secrets.
OFF by default. Enabled, the chart renders two Password generators and an ExternalSecret that produces the Secret Shepherd reads — so the encryption key and the first administrator's password are generated in-cluster and never pass through your shell, your values file, or your terminal history.
Requires the External Secrets Operator and its CRDs; the chart does not install operators. No SecretStore is needed: a generator is the source.
refreshInterval is "0" and MUST stay "0". These are not rotatable credentials: regenerating the encryption key would leave every git credential and OIDC client secret already stored in the database undecryptable, with no error at the moment it happens. deletionPolicy is Retain for the same reason — uninstalling the release must not take the key with it.
Both only hold while the ExternalSecret itself survives, so the chart also skips rendering it once it exists. Changing externalSecrets.* after the first install therefore has no effect; delete the ExternalSecret deliberately if you genuinely want it regenerated, understanding that a new key orphans every credential the old one encrypted.
The same GITOPS WARNING as cnpg above applies, and here the loss is quieter: under Argo CD or Flux the ExternalSecret is recreated on every sync, syncs once against fresh Password generators, and replaces an encryption key that cannot be rotated -- with no error at the moment it happens. Set render: never below once the secret exists.

KeyDefaultDescription
externalSecrets.enabledfalseenabled: turn on to let External Secrets Operator generate the bootstrap Secret in-cluster. See the block comment above for what that means and its GitOps caveat.
externalSecrets.renderautorender: auto | always | never. Identical meaning to cnpg.render above.
externalSecrets.apiVersionexternal-secrets.io/v1API versions, exposed because ESO has moved them before. These defaults match ESO v1.x.
externalSecrets.generatorApiVersiongenerators.external-secrets.io/v1alpha1generatorApiVersion: API version for the Password generator objects (distinct from apiVersion above, which is for the ExternalSecret itself).
externalSecrets.refreshInterval"0"Do not change. See the note above.
externalSecrets.encryptionKey.length3232 characters, base64-encoded by the ExternalSecret template into the 32 bytes Shepherd requires. DO NOT CHANGE: Shepherd rejects any other length outright, so a different value here produces an instance that cannot start. Exposed only because the generator requires the field.
externalSecrets.bootstrapAdmin.enabledtrueGenerate the first administrator's password too. Turn this off if you would rather set SHEPHERD_BOOTSTRAP_ADMIN_PASSWORD yourself.
externalSecrets.bootstrapAdmin.length24length: character length of the generated bootstrap administrator password.
externalSecrets.bootstrapAdmin.loginadminRead it once it exists with: kubectl get secret <release>-secrets \ -o jsonpath='{.data.SHEPHERD_BOOTSTRAP_ADMIN_PASSWORD}' | base64 -d

existingSecret

KeyDefaultDescription
existingSecret""existingSecret: the name of a Secret you already manage, holding the SHEPHERD_* environment variables. Empty means the chart renders its own from secrets below. Set this and secrets is ignored entirely; it is also mutually exclusive with externalSecrets.enabled, which the chart refuses rather than silently picking a winner.

secrets

KeyDefaultDescription
secrets{}secrets: key-value pairs rendered into a Kubernetes Secret and injected as environment variables.
Convenient, and the least private of the three options: whatever you put here is stored verbatim in the Helm release and stays readable through helm get values <release> for the life of the release history. For production prefer existingSecret (you manage the object) or externalSecrets.enabled (the cluster generates it and it never passes through your shell at all). Keys must match the SHEPHERD_* env var names. Example for local admin password hash: secrets: SHEPHERD_DATABASE_URL: "postgres://..." SHEPHERD_SECURITY_ENCRYPTION_KEY: "base64-32-bytes" SHEPHERD_BOOTSTRAP_ADMIN_PASSWORD: "choose-something" NEVER put SHEPHERD_BOOTSTRAP_ADMIN_PASSWORD in the config: block above — that renders into a ConfigMap, which is not a place for a password.

migrations

KeyDefaultDescription
migrations.job.enabledtrueenabled: run shepherd migrate up as a pre-install/pre-upgrade hook, so the schema is always current before the new pods start. Turn it off only if you run migrations yourself (shepherd migrate up against the same database) BEFORE every upgrade -- Shepherd will not start against a schema older than its binary.
migrations.job.backoffLimit6How many times the migration Job may fail before the release does. The default covers a database that is still being provisioned -- see the Job template. Lower it if you would rather fail fast against a database that is always already there.
migrations.job.resources{}resources for the migration pod. Empty means unbounded, which is fine on most clusters; set it if a ResourceQuota or a LimitRange in this namespace requires every pod to declare one, since the Job is a pre-install hook and a rejected hook pod fails the whole install.

route

Gateway API HTTPRoute. OFF by default, like ingress below: it needs the Gateway API CRDs, which are not present on a vanilla cluster, so defaulting it on made a plain helm install fail with "no matches for kind HTTPRoute". Templating could never catch that — helm template does not check whether a Kind exists — and every values file in the repo already set it to false, which is how the broken default survived. Enable it deliberately, and set parentRefs/hostnames when you do: an HTTPRoute with neither routes nothing.

KeyDefaultDescription
route.enabledfalseenabled: turn on to render the HTTPRoute below. See the comment above for why it defaults off.
route.hostnames[]hostnames: hostnames this HTTPRoute matches, e.g. ["shepherd.example.com"]. Required alongside parentRefs -- an HTTPRoute with neither routes nothing.
route.parentRefs[]parentRefs: the Gateway(s) this HTTPRoute attaches to, e.g. [{name: my-gateway, namespace: gateway-system}]. Required alongside hostnames.

metrics

--------------------------------------------------------------------------- Metrics
Shepherd serves Prometheus metrics on a SEPARATE listener from the API (config.server.metrics_listen, default :9090). /metrics on the main port is deliberately 404-guarded, so anything scraping :8080/metrics gets nothing — which is what the ServiceMonitor here used to do.
enabled controls the metrics Service and its container port. It is on by default: the listener runs regardless, and a ClusterIP Service in front of it exposes nothing outside the cluster. Turn it off only if you have a policy against unscraped Services existing. ---------------------------------------------------------------------------

metrics.serviceMonitor.interval"30s"interval: Prometheus scrape interval for this target. Empty uses the Prometheus Operator's own default.
metrics.serviceMonitor.scrapeTimeout"10s"scrapeTimeout: how long Prometheus waits for a scrape before giving up. Empty uses the Prometheus Operator's own default.

metrics.serviceMonitor.metricRelabelings[]metricRelabelings: standard Prometheus Operator relabeling rules applied to each scraped metric after collection (e.g. to drop or rename series). Empty applies none.

networkPolicy: a NetworkPolicy for SHEPHERD's own pods (the simulator has its own, far stricter one under simulator.networkPolicy).
Enabled, it allows ingress from any namespace in the cluster to the API port and the metrics port, and allows all egress — Shepherd has to reach your database, your identity provider and your git remotes, and the set of those is not something the chart can know. simulator

----------------------------------------------------------------------------- S3 sandbox simulator (VB-1 §6.4) — ENABLED BY DEFAULT since v0.0.1, after both containment gates closed (docs/project-status.md F5: B-CONTAIN-1 fixed and red/green-proven; NetworkPolicy enforcement verified in a real cluster by e2e/k8s/simulator_containment_test.go's probes and kill probe).
TO DISABLE: set simulator.enabled: false below (or --set on install) — nothing simulator-related renders, and shepherd's config is not wired to it. The compose stacks keep their opt-in sim profile: that is test-environment design (the default make e2e deliberately exercises the simulator-absent path), not the product default.
When enabled, shepherd's config is wired to this chart's simulator Service automatically unless you set config.simulator yourself — an explicit config.simulator block always wins verbatim (see templates/configmap.yaml).
It runs USER-AUTHORED Alloy configuration. Every control below is load-bearing, not decoration, and every one is asserted by deploy/helm/chart_test.go so it cannot regress silently: - automountServiceAccountToken: false on its ServiceAccount. Defense in depth, not the only gate — internal/simsvc.Config.SATokenPath makes the binary itself refuse to start if a token is mounted anyway. - a bearer token (simulator.token below) on the control API. Without one POST /v1/runs was reachable by anything that could route to the Pod at all; every install now authenticates it, from one of three sources. - a default-deny egress NetworkPolicy. The sandboxed Alloy is a CHILD PROCESS of shepherd-simulator (internal/simsvc/runner.go), not a sibling container, so this Pod's own network boundary IS the sandbox's boundary. Egress is allowed only to this Pod's own harness ports (the capture receivers shepherd-simulator itself serves) — nothing else, including cluster DNS (D10: every harness endpoint the sandbox needs is dialled by loopback IP, so it has no legitimate reason to resolve a name at all), the rest of the cluster, or the internet. - non-root securityContext, every capability dropped, no privilege escalation, a read-only root filesystem (the run scratch directory is an emptyDir mounted over /tmp). - CPU/memory limits, so one runaway sandboxed config cannot starve the node. - what this chart CANNOT set: a per-Pod process/PID limit. Kubernetes has no PodSpec field for one (unlike the compose stacks' pids_limit) — it is a kubelet-level setting (podPidsLimit in KubeletConfiguration, or --pod-max-pids) that belongs to the cluster operator, not this chart. Mitigating factors: the sandboxed Alloy is one process (internal/simsvc runs it directly, no shell fork-bomb surface), and the CPU/memory limits above already bound a runaway config's other resource costs.
See docs/visual-builder-design-VB1.md §6.4 and docs/archive/reviews/s3-sandbox-security-findings.md (finding H5) for why each of these exists.
