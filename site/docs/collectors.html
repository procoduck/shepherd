Docs/Fleet/Connect a collector

Connect a collector

Add a remotecfg block to the collector's config.alloy. Shepherd resolves the collector by its cluster and role attributes — role is one of metrics, logs, singleton, or receiver.

config.alloy
remotecfg {
  url = "http://shepherd:8080"
  basic_auth {
    username = "<token-uuid>"
    password = "<token-secret>"
  }
  attributes = {
    cluster = "<cluster-name>",
    role    = "metrics",
  }
  poll_frequency = "60s"
}

On first poll, an unclaimed cluster gets served an empty config so it keeps running whatever it already has locally — nothing is disrupted until the cluster belongs to an organisation and someone with edit rights in that organisation enables pipelines that match it. A collector authenticating with an agent token an app admin created or bound, or with OIDC under a binding, claims its unclaimed cluster for its token’s organisation on its first poll; otherwise an app admin claims the cluster (Roles).

The served config includes a self-monitoring beacon that writes back to Shepherd. Its remote-write URL is built from Shepherd’s server.base_url, so that address must be reachable from every collector’s cluster, not just from your browser. With agent-token auth, the beacon reads the token from the collector’s environment, so every collector must expose it as environment variables named exactly SHEPHERD_AGENT_TOKEN_ID and SHEPHERD_AGENT_TOKEN_SECRET (with OIDC beacon auth, SHEPHERD_OIDC_CLIENT_ID and SHEPHERD_OIDC_CLIENT_SECRET instead).

Collector status

Each collector shows the status its Alloy last reported for the config it was served:

  • APPLIED — Alloy loaded the config it was served.
  • FAILED — Alloy rejected it, and the collector page shows Alloy’s own error. The collector keeps running its previous config. A config can pass Shepherd’s validation and still fail here, for reasons only the host knows (a file path that does not exist there, Kubernetes discovery outside Kubernetes). When the error’s line falls inside a pipeline, the collector page, its Reconciliation tab and the pipeline’s own page say rejected in pipeline X (line N of its text, line M of the merged config); when the error belongs to an earlier served config, the page says that instead.
  • APPLYING — Shepherd is serving a new config and Alloy has not reported on it yet. It lasts until the collector’s next poll, then turns APPLIED or FAILED. An APPLIED is always about the config being served now, never an earlier one; a FAILED collector served a new config stays FAILED until Alloy reports again.
  • UNKNOWN — nothing reported yet, for example a collector that has not polled since it was created.

With agent.inactive_after set, an instance that has not polled for that long shows as inactive, whatever it last reported, and a collector shows inactive once all its instances are. Its last reported status is kept, not reset: when it comes back it shows that status again (a FAILED collector stays FAILED) until Alloy reports something new. On Kubernetes each Alloy restart registers a new instance, so the replaced pod’s row turns inactive while the new one carries the status.

Version warnings

A save is checked against the Alloy versions of the collector’s active instances (Your collectors’ Alloy versions), but the instances can change afterwards — an older pod joins. Shepherd keeps serving the validated config and checks it again when it hands it out. When that finds something, the Collectors list marks the version MISMATCH (an instance’s version lacks part of the config, so that instance will most likely reject it and keep its last config) or NOTE (a version checked against an approximate or the pinned schema, or a component that needs a --stability.level flag), and the collector page lists each finding. Each change is recorded once in the audit log as collector.version_warning, and a version that keeps changing is checked at most once a minute. The warning clears on its own soon after the old pod goes inactive.

A collector’s page has tabs for its Served Config (the exact merged config it receives), Pipelines (the pipelines that config is built from and the ones left out, below), Reconciliation (whether what its role declares, what it is served and what its beacon reports agree), Info (its instances), and Attributes & Labels, where an org admin sets labels that pipelines can match on (Matchers); org admins also get Access, its group assignments.

The served config starts with // Generated by Shepherd, then lists each pipeline it includes with its revision, (rev N), and names any pipeline left out for its role and why. Any change to that text — including a revision bump with unchanged pipeline text — makes the collector reload once on its next poll.

The Pipelines tab says why that config holds what it does. Under Contributing is each pipeline in it, linked to its editor, with the revision served, each of its matchers next to the value the collector has for that label (a git pipeline says it matched by its repo link), and the lines its block occupies in the served config; choosing the lines opens the Served Config tab with the block highlighted. The self-monitoring baseline is listed too, marked as such. Under Excluded is each pipeline that matches the collector but was left out, with the reason — Role (its signals are ones the collector’s role does not allow), Strict tenant check (with the check’s finding) or Unparsable matcher. Shepherd records all of this when it builds the served config, so the tab always describes the config the collector is actually served. A config built before this was recorded says so; it is recorded on the collector’s next poll. An Alloy version mismatch never excludes a pipeline — it is the version warning above.

With Grafana's k8s-monitoring chart

If your clusters run Grafana's k8s-monitoring Helm chart, Shepherd writes the values for you. On Collectors, an organisation admin chooses Connect a cluster, names the cluster and picks its collectors (metrics, logs, singleton, receiver). Shepherd returns:

  • shepherd-layer.yaml — each collector's remoteConfig, pointed at this Shepherd's server.base_url, with the cluster name and role as attributes and the organisation's default tenant if it has one;
  • shepherd-credentials.yaml — loads the agent token into each collector from a Kubernetes Secret (it names the Secret; it never contains the token);
  • the kubectl create secret and helm upgrade --install commands that use them.

Apply both files next to your own values — they set nothing else, so sizing, features and destinations stay yours. The values are checked against the k8s-monitoring version they name, and Shepherd's test suite installs that exact chart with them and watches a collector register and load a pipeline.

The Secret needs an agent token for your organisation (Access → Agent Tokens). A token an app admin created claims the cluster for the organisation on the collectors' first poll. A token an organisation admin created is served only for a cluster an app admin has already claimed for the organisation (Admin → Clusters); until then its collectors are refused. The dialog says which of those the cluster still needs. A cluster name another organisation already owns is refused.
