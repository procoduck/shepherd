## 2. Decisions

### 2.1 Strict component allowlist (#421)

- A strict org may use only components with a shipped strict classification in the schema overlay:
  allowed, allowed with the existing attribute checks, or refused, each with a one-line reason. A
  repo test fails when a schema (an Alloy bump) brings a component nobody has classified.
- App admins may allow an extra component **per org**. The component still gets every existing
  strict check (tenant ids, headers, label maps, capture-group labels); the UI and the audit log
  show it as admin-allowed and unreviewed.
- Rollout is the 0.20 mechanism: refused at save; a stored pipeline that fails is excluded at serve
  time (served header, `strict_tenant_excluded` reconciliation finding, one audit row per change);
  `shepherd admin tenant-preflight` lists such pipelines before the upgrade.
- A new CI suite runs real Alloy against a recording sink for every construct strict mode refuses
  and every one it accepts, and checks the tenant the sink receives. It runs on PRs touching
  `internal/validate`, `internal/serve`, `internal/tenancy`, `internal/pinnedimport` or the schema
  overlay, weekly, and on Alloy bumps.
- The adversarial reviewer signs off the classification.

### 2.2 Post-0.20 follow-ups (#422)

All four from `docs/project-status.md` §4: Reconciliation after the sweep (a per-instance
last-report record that outlives the beacon rows, a migration); the wizard preview's warning count;
specs for malformed and flapping version strings; and the trailing `// otelcol.exporter.loki`
comment kept next to the exporter in a strict org's served form (an approved served-text change:
strict-org collectors reload once).

### 2.3 F-CONTRIB (#423)

The collector page lists each contributing pipeline (link, the matcher that matched, its line span
in the served config) and each excluded pipeline with its reason (role, strict tenant check,
version). An additive proto field is approved.

### 2.4 Sandbox run window (#424)

A run is extended to cover two of the longest scrape or poll intervals in the pipeline, capped at
the existing maximum run length; the run page says why it ran longer.

### 2.5 Chart and code (#425)

The kind suite installs the previous published chart and `helm upgrade`s to the new one;
`NOTES.txt` prints each route's real scheme; `pipelines.source` becomes a distinct Go type so the
`exhaustive` linter checks switches over it.

### 2.6 Canvas accessibility and nested bindings (#426)

Everything doable on the canvas is doable from the keyboard: moving between nodes, visible focus
on nodes and ports, creating and deleting edges, screen-reader labels, and an axe check in the
mocked UI suite. Nested-block bindings round-trip through `doc.bindings[]` via an additive prop
path; a proto change, if one turns out to be needed, goes back to the owner first.
