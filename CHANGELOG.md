# Changelog

Written by hand, because the autogenerated kind is a list of `feat:` commits and this project
builds a lot of things behind review gates. A commit landing is not the same as a capability
shipping, and a changelog that conflates them tells operators to plan against work they cannot
use. Each entry below says which it is.

Categories used here:

- **Shipped** — reachable in a running deployment.
- **RPC only** — the API exists and is callable; there is no UI.
- **Built, not wired** — the code and tests exist, nothing calls them in production yet.

## v0.21.0

Chart 0.25.0, released 2026-10-28. **Strict tenant mode accepts only classified components** and
**checks gateway route endpoints**, the collector page shows **which pipelines its served config
is built from** (and which matched but were left out, and why), **sandbox runs last long enough to
see a scrape**, and the visual builder's **canvas works from the keyboard** and binds secrets
**into nested blocks**. Before upgrading, run `shepherd admin tenant-preflight` if any org uses
strict tenant mode (or `tenants.require_owned` is on): the component allowlist and the gateway
route endpoint check can exclude stored pipelines from served config until they are fixed, and
the preflight lists them. If collectors reach the tenant-route gateway by names other than
`gateway.routes.public_base_url`'s host, list those names in `gateway.routes.hosts`
(`SHEPHERD_GATEWAY_ROUTES_HOSTS`) first, so the preflight and the server check what you expect.
Migrations `0047`–`0050` are additive. The served config format moves from 4 to 5: every cached
row recomputes once, to identical bytes, so no collector reloads. A strict org's served text
changes in two documented cases besides newly excluded pipelines: a comment trailing an
`otelcol.exporter.loki` block now stays with the exporter, and the header's exclusion reason for
an endpoint under the org's own revoked route (or a route whose tenant it no longer owns) says so
— those collectors reload once. Upgrade the simulator image together with the server. First
published as the prerelease v0.21.0-rc.1 (entry below); this entry covers everything since
v0.20.0.

**Upgrade:** `helm upgrade` to chart 0.25.0 — read `deploy/helm/shepherd/UPGRADING.md`
(0.24.x → 0.25.0) first and follow its steps in order:

1. **Strict tenant mode only: set the gateway hosts, then run the preflight.** Set
   `gateway.routes.hosts` (chart: `config.gateway.routes.hosts`) if collectors reach the gateway
   by more names than `public_base_url`'s host, then run `shepherd admin tenant-preflight` with
   the new image. Each pipeline it lists says how to fix it: a component finding — replace the
   component, or have an app admin allow it for the org; a route finding — send to one of the
   org's own routes; a tenant finding — assign the tenant to the org; text that does not parse —
   fix the text. With `tenants.require_owned` on, the server does not start while it lists
   anything. (#421, #431, #434, #439)
2. **HTTPRoute installs:** set `route.scheme` (`http` or `https`) if the install notes should print
   a scheme the first `parentRef`'s port does not imply. Chart notes only. (#425)
3. **Upgrade the server and simulator images together** (both follow the chart's `appVersion`
   unless you pin `image.tag` / `simulator.image.tag`): the simulator's results encoding changed
   for non-finite samples. (#435)
4. **Migrations `0047`–`0050`** run in the pre-upgrade Job, all additive; then every served-config
   row recomputes once under format 5, to the same bytes. New proto fields are additive. (#421,
   #428, #432, #433)

### Added

- **Strict tenant mode accepts only classified components.** Shipped. Every component of every
  shipped schema carries a strict classification in the schema overlay
  (`internal/schema/artifacts/overlay.json`, `components.<name>.strict`, and `strict_retired`
  for a component only an older shipped schema has): `allowed` (it cannot introduce or alter a
  tenant label or header), `checked` (it can, only through attributes the tenant lint already
  checks, each check named), or `refused` (it can produce tenant-affecting output the lint cannot
  prove), each with a one-line reason. In a strict org a component classified refused (today only
  `otelcol.auth.google`, whose `token_header` may name `X-Scope-OrgID`), or not classified at
  all, is refused wherever the lint walks — the top level, a declare, a `foreach` template, a
  literal or pinned module — with a message naming it; declare and module instances are judged by
  their bodies, and Alloy's own blocks are left to Stage 2. A name a shipped schema has is always
  judged as that built-in component, whatever import labels are in scope: an import label can no
  longer stand in for a component name, and any other dotted name counts as a module instance
  only when it is exactly `<label>.<declare>` for an import whose module the lint read. A repo
  test fails when an Alloy bump brings a component nobody has classified, or a `checked` entry
  names a check that does not exist or does not cover the component. Everything the
  grafana/k8s-monitoring chart, Shepherd's wizards and the baseline emit is allowed or checked.
  Refused at save (every write path, Stage 3 and the git-sync dry runs included); a stored
  pipeline that fails is excluded at serve time, with the served header, a
  `strict_tenant_excluded` reconciliation finding and one audit row per change. (#421, PR #429)
- **Strict tenant mode checks gateway route endpoints.** Shipped. In a strict org every endpoint,
  on any host, whose path starts with `otlp` or `faro` and a string shaped like a route segment
  must be under one of the org's own live routes (active, or deprecated during its rotation
  overlap) whose tenant the org owns; the path is read as a gateway may read it, and vendors' OTLP
  paths are untouched. On the gateway's configured hosts (`gateway.routes.public_base_url`'s and
  the new `gateway.routes.hosts`, `SHEPHERD_GATEWAY_ROUTES_HOSTS`, comma-separated) every
  endpoint must be under an owned route, written plainly, and a `proxy_url`, a `Host`/`:authority`
  header, Datadog's `site` or a blackbox module setting naming them is refused. An endpoint the
  lint cannot read is refused once the installation has a live tenant route or a gateway host is
  configured, unless its literal start completes the path. The new `gateway_endpoints` check is
  named on the 71 components with an endpoint attribute (23 moved from `allowed` to `checked`).
  Creating, rotating or revoking a route recomputes the org's served configs. A value in `hosts`
  that is not a host name or IP address stops the server from starting. (PR #431)
- **`prometheus.exporter.blackbox` and `stage.truncate` in strict tenant mode.** Shipped. A strict
  org's blackbox exporter `config` must be a literal YAML config that names `X-Scope-OrgID`
  nowhere and has no tcp `query_response` (`config_file` is refused); a `loki.process`
  `stage.truncate` label rule needs a literal `sources` list without `__tenant_id__`. The blackbox
  wizard's modules pass unchanged. (#421, PR #429)
- **Admin-allowed components per org.** Shipped. An app admin may allow a component strict mode
  refuses for one org (Admin → Organisations → Edit → Admin-allowed components;
  `AdminService.List/Add/RemoveOrgStrictComponent`, audited as `org.strict_component.add` /
  `.remove` with `reviewed: false`). It lifts only that refusal — every other strict check still
  applies — and the UI marks each entry "admin-allowed, unreviewed". Only a shipped component
  classified refused can be allowed; removing an entry is refused while the org is strict and an
  enabled pipeline uses it. Both changes recompute the org's served configs. Migration `0047`.
  (#421, PRs #429, #431, #434)
- **The collector page shows the pipelines its served config is built from.** Shipped. A new
  **Pipelines** tab lists each contributing pipeline (a link, the revision served, each matcher
  with the collector's value for its label, and the lines of its declare block in the served
  config, which open the Served Config tab highlighted — a link that can be shared,
  `?tab=config&lines=31-36`), the self-monitoring baseline's lines, and each pipeline that matched
  but was excluded, with the reason (`role`, `strict_tenant` with the check's finding, or
  `unparsable_matcher`). It is recorded by the same assembly that writes the served bytes and
  stored with them (`serve_cache.provenance`, migration `0049`), so it cannot disagree with what
  is served. `serve.Format` 5 makes each row recompute once, to the same bytes, so the column
  fills in without a reload. (#423, PRs #432, #434)
- **Sandbox runs cover the pipeline's scrape interval.** Shipped. `CreateRun` extends a run to two
  of the longest scrape or poll intervals in the pipeline, capped at the maximum run length (120s,
  or `simulator.max_duration` when lower), and never shortens what was asked for; components the
  sandbox stubs or removes (secret sources such as `remote.kubernetes.secret` among them) do not
  count. The run dialog says why the run is longer and counts down from the effective duration.
  Migration `0050`. (#424, PRs #433, #439)
- **The visual builder's canvas works from the keyboard.** Shipped. Tab into the canvas and the
  arrow keys move between nodes (Home/End: first/last); Space selects, I opens the Properties
  panel, Shift+arrows move a node 8px, Delete removes it with its wires. Enter goes into a node's
  ports, Enter on a port starts a wire and the arrows then visit only the ports it can connect to;
  Enter connects, Escape cancels. Wires are Tab stops and delete with Delete. Every keyboard edit
  is one undo step, and a viewer stays read-only. `?` opens the shortcut sheet. Nodes, ports and
  wires carry screen-reader names, every keyboard action is announced in a polite live region,
  and keyboard focus draws a ring in a new `--color-focus` token (3:1 on every canvas surface in
  both themes). (#426, PR #438)
- **Bindings into nested blocks.** Shipped. A `doc.bindings[]` entry's `prop` may be a path into
  the component's nested blocks — `endpoint[0].basic_auth.password`, `client.tls.ca_pem`,
  `stage.tenant[0].value` — and both renderers write the expression inside that block. The
  inspector's binding picker writes these entries, shows them on the field and lists every binding
  a node holds in a new Bindings section with Unbind; the read-only graph view reports references
  at the same path. A prop with no `.` and no `[` keeps its old meaning and byte-identical
  rendering; the path travels in `GraphBinding.prop`, so no proto field was added. A path is
  capped at 32 segments and 256 bytes (`binding_path_invalid`). (#426, PR #438)

  follows the findings: assign the tenant (a tenant finding), use one of the organisation's tenant

  component classified refused), or "fix the pipeline text" for a stored pipeline whose text does

- **The chart's install notes print each URL's real scheme.** Shipped. An Ingress host is `https`
  only when an `ingress.tls` entry covers it; an HTTPRoute's scheme is the new `route.scheme` value
  (`http` or `https`), inferred from the first `parentRef`'s port when empty (80 is `http`, 443 is

  port-forward instructions spell out the `http://` URL. No rendered object changes. (#425, PR
  #437)
- **Undo straight after opening a visual pipeline no longer empties the canvas.** Shipped. Opening,
  importing, reloading or switching to a pipeline, and restoring a draft, start a fresh undo
  history. (PR #439)
- **The Reconciliation tab reads "nothing running", not "unknown", after the sweep.** Shipped. Each
  instance's last report is kept in its own record (migration `0048`, `beacon_instance_reports`),
  swept with the instance lifecycle rather than with the beacon rows. (#422, PR #428)
- **Junk and flapping `collector.version` strings.** Shipped. Versions in the version check's
  audit row and fingerprint are trimmed and cut to 64 bytes, at most 256 of them; a flapping
  unknown version no longer writes an audit row per re-check; a NUL byte in a local attribute or
  the instance id answers `InvalidArgument` rather than `Internal`. (#422, PR #428)
- **A comment trailing the `otelcol.exporter.loki` block stays with it.** Shipped. In a strict
  org's served form the inserted `loki.process "shepherd_tenant_drop_<label>"` block goes after a
  comment that ends the exporter's closing line. Only the served text of a strict org's pipeline
  with such a comment changes (its collectors reload once). (#422, PR #428)
- **A refusal for the organisation's own unusable route says why.** Shipped. "…which is this
  organisation's route, but it is revoked" or "…but its tenant "x" is no longer one the
  organisation owns"; another organisation's segment keeps the neutral wording. The reason is also
  printed in the served header's strict tenant exclusions. (PR #434)
- **Admin-allowed component messages** say which case a refusal is, and the editor notes that an
  allowed public-preview or experimental component still needs the collector's
  `--stability.level`. (PR #434)
- **The sandbox run-window note no longer names a component the sandbox removes.** Shipped. (PR
  #439)
- **A sandbox run whose captured samples include NaN or ±Inf completes.** Shipped. Captured
  first/last values travel as a JSON number when finite and as `"NaN"`, `"+Inf"`, `"-Inf"` or
  `"StaleNaN"` otherwise, and the simulator's control API encodes a response in full before
  sending it (a failure answers 500 `encode_failed`). Upgrade the simulator image with the server.
  (PR #435)

## v0.21.0-rc.1 (prerelease)

Chart 0.25.0-rc.1, a **release candidate** for v0.21.0. It is published as a GitHub prerelease:
`:latest` does not move, and `helm install` without `--version 0.25.0-rc.1` (or `--devel`) keeps

contributing and excluded pipelines, and the sandbox run window — plus the fixes from its
pre-tag kind walkthrough. See `deploy/helm/shepherd/UPGRADING.md` (0.24.x → 0.25.0) before
upgrading.

**Strict tenant mode accepts only classified components.** Run `shepherd admin tenant-preflight`
before upgrading if any org uses strict tenant mode: a stored pipeline that uses a component the
schema overlay classifies `refused` (or one no shipped schema classifies) is excluded from served
config until it is fixed or an app admin allows the component for its org. Strict tenant mode
also checks gateway route endpoints: a stored pipeline sending under another organisation's tenant

the check cannot read, is excluded the same way. Migration `0047` is

### Added

- **Strict tenant mode accepts only classified components.** Shipped. Every component of every
  shipped schema now carries a strict classification in the schema overlay
  (`internal/schema/artifacts/overlay.json`, `components.<name>.strict`, and `strict_retired`
  for a component only an older shipped schema has): `allowed` (it cannot introduce or alter a
  tenant label or header), `checked` (it can, only through attributes the tenant lint already
  checks, each check named), or `refused` (it can produce tenant-affecting output the lint cannot
  prove), each with a one-line reason. Of the 187 shipped components, 82 are allowed, 104 checked
  and 1 refused (`otelcol.auth.google`: its `token_header` may name `X-Scope-OrgID`). In a strict
  org a component classified refused, or not classified at all, is refused wherever the lint
  walks — the top level, a declare, a `foreach` template, a literal or pinned module — with a
  message naming it; declare and module instances are judged by their bodies, and Alloy's own
  blocks (`logging`, `argument`, …) are left to Stage 2. A repo test fails when an Alloy bump
  brings a component nobody has classified, or a `checked` entry names a check that does not
  exist or does not cover the component. Everything the grafana/k8s-monitoring chart, Shepherd's
  wizards and the baseline emit is allowed or checked. The rollout is 0.20's: refused at save
  (every write path, Stage 3 and the git-sync dry runs included), and a stored pipeline that fails
  is excluded at serve time, with the served header, a `strict_tenant_excluded` reconciliation
  finding and one audit row per change; `shepherd admin tenant-preflight` lists such pipelines.
  (#421)
- **Strict tenant mode checks gateway route endpoints.** Shipped. Shepherd's tenant routes set
  the tenant themselves (`/otlp/<segment>`, `/faro/<segment>`) and name no host, and segments are
  unique across the installation and never reused. So in a strict org every endpoint, on any
  host, whose path starts with `otlp` or `faro` and a string shaped like a route segment must be
  under one of the org's own routes: a live route (active, or deprecated during its rotation
  overlap) of that kind whose tenant the org owns. The path is read as a gateway may read it
  (percent-decoded, backslashes as slashes, `.`/`..` and empty segments resolved, case-folded),
  element by element as the route's prefix match is; vendors' OTLP paths (Grafana Cloud's `/otlp`
  and `/otlp/v1/...`, `/v1/traces`) are untouched. The gateway's hosts, when configured
  (`gateway.routes.public_base_url`'s and the new `gateway.routes.hosts`,
  `SHEPHERD_GATEWAY_ROUTES_HOSTS`, comma-separated), add a stricter rule there: every endpoint on
  them must be under an owned route, written plainly, and a `proxy_url`, a `Host`/`:authority`
  header, Datadog's `site` or a blackbox module setting naming them is refused. Hosts are compared
  as a client resolves them (case, trailing dot, IDN, percent-encoding and numeric IPv4 forms
  normalised, on every port). An endpoint the lint cannot read — a function call, a component
  export, `sys.env`, a value a declare is given in a `foreach` template — is refused whenever the
  installation has a live tenant route or a gateway host is configured, unless its literal start
  completes the path (a `?` or `#` follows it); declare and module arguments are followed to
  literals as for tenants. Which attributes are endpoints is read from every shipped schema (a
  URL, endpoint, address, host or server attribute, less listen addresses, TLS server names,
  OAuth2 token URLs and non-HTTP protocols); the new `gateway_endpoints` check is named on all 71
  components that have one, and 23 moved from `allowed` to `checked` for it: `beyla.ebpf`,
  `discovery.consulagent`, `.nerve`, `.openstack`, `.ovhcloud`, `.serverset`, `.triton`,
  `otelcol.exporter.awss3`, `.datadog`, `.googlecloud`, `.googlecloudpubsub`, `.splunkhec`,
  `otelcol.processor.resourcedetection`, `prometheus.exporter.apache`, `.cadvisor`, `.consul`,
  `.databricks`, `.elasticsearch`, `.github`, `.squid`, `.unix`, `remote.s3` and `remote.vault`.
  The repo test fails when a component with an endpoint attribute does not name the check, and a
  spec pins that Shepherd's wizards, baseline, dev seed and the k8s-monitoring fixtures pass.
  Refused at save, excluded at serve time and listed by `shepherd admin tenant-preflight`, as the
  other checks; creating, rotating or revoking a route (and the rotation overlap ending) marks the
  org's served configs dirty and recomputes them — the installation's first live route and its
  last revoke mark every served config — and the serve-time verdict cache is keyed by the
  gateway's hosts, whether routes are in use, and the org's routes.
- **`prometheus.exporter.blackbox` in strict tenant mode.** Shipped. A probe sends the requests
  its modules define, so in a strict org the blackbox exporter's `config` must be a literal YAML
  config that names the `X-Scope-OrgID` header nowhere (keys and strings, case-insensitively,
  after YAML decoding) and has no tcp `query_response`; `config_file` is refused. The blackbox
  wizard's modules pass unchanged. Likewise a `loki.process` `stage.truncate` rule with
  `source_type = "label"`, which cuts each label value it names and appends a suffix, needs a
  literal `sources` list without `__tenant_id__`. (#421)
- **Admin-allowed components per org.** Shipped. An app admin may allow a component strict mode
  refuses for one org (Admin → Organisations → Edit → Admin-allowed components;
  `AdminService.List/Add/RemoveOrgStrictComponent`, audited as `org.strict_component.add` /
  `.remove` with `reviewed: false`). It lifts only that refusal — every other strict check still
  applies to the component — and the UI marks each entry "admin-allowed, unreviewed". Only a
  component a shipped schema has (`strict_retired` included) whose classification is refused can
  be allowed; one strict mode already accepts, and any other name, is refused (`invalid_argument`),
  and the refusal of a name no shipped schema has, or of a module instance whose module or
  declare was not found, no longer suggests allowing it; removing an entry is refused
  (`failed_precondition`, naming the pipelines) while the org is strict and an enabled pipeline
  uses it, as for the import allowlist (only enabled pipelines are checked; a disabled one that
  uses the component is refused when it is enabled). Both changes recompute the org's served configs.
  Migration `0047` adds `org_strict_components`. (#421)
- **The collector page shows the pipelines its served config is built from.** Shipped. A new
  **Pipelines** tab lists each contributing pipeline (a link to it, the revision served, each
  matcher with the collector's value for its label — or "git repo link" — and the lines of its
  declare block in the served config, which open the Served Config tab with the block
  highlighted), the self-monitoring baseline's lines, and each pipeline that matched but was
  excluded, with the reason (`role`, `strict_tenant` with the check's finding, or
  `unparsable_matcher`). It is recorded by the same assembly that writes the served bytes
  (`merge.Assemble` → `serve.ComputeServed`) and stored with them (`serve_cache.provenance`,
  migration `0049`), so the tab never re-evaluates matchers and cannot disagree with what is
  served; a view reads the cached row. `GetServedConfigResponse` gains `provenance_recorded`,
  `contributing`, `excluded` and `baseline_lines` (additive). Served bytes and hashes are
  unchanged; `serve.Format` 5 makes each row recompute once, to the same bytes, on its
  collector's next poll so the column fills in without a reload. (#423)
- **Sandbox runs cover the pipeline's scrape interval.** Shipped. A sandbox run used to observe for
  the 30 seconds the menu asks for, so a `prometheus.scrape` at its 60-second default could end
  before it scraped at all. `CreateRun` now extends the run to two of the longest scrape or poll
  intervals in the pipeline (scrape, poll, collection, sync, refresh and connector flush

### Added

- **Agent tokens are bound to an organisation.** Shipped. A token carries an org and optional
  cluster and role allowlists, resolved exactly like an OIDC collector binding: it is refused
  (`claim_denied` / `role_denied`) for a cluster another org claims or outside its allowlists, and
  claims an allowed unclaimed cluster for its org only when an app admin minted or bound it
  (`AgentToken.may_claim`). Org admins (and admin-tier service accounts) can create, list and
  revoke their own org's tokens, which serve only clusters the org already claims. The Agent
  Tokens page moved under **Access**, shows each token's org and allowlists, lists unbound tokens
  first and offers **Bind** / **Rebind** to an app admin; `shepherd token bind` is new. A bound
  token's beacon write naming another org's collector is dropped (`reason="beacon_denied"`). (#386)
- **An organisation can own several tenants and tenant prefixes.** Shipped. An app admin adds
  exact tenants and prefixes on **Admin → Organisations** (Edit) and picks the default; a tenant
  belongs to at most one organisation, so overlaps across orgs are refused. A tenant can be
  removed unless a live route, destination or binding of the org would be left on a tenant it no
  longer owns. Tenant routes take a tenant the org owns (picker in the route form, default
  preselected, a new Tenant column), destination bindings refuse another org's tenant as
  destinations did, and chart values use the default tenant. Every write is audited
  (`org.tenant.add|remove|set_default`). (#387)
- **Strict tenant mode** (opt-in, off by default). Shipped. Per organisation (an app admin's toggle
  on **Admin → Organisations**, `SetOrgStrictTenants`) or for every org
  (`config.tenants.require_owned`), an org's destinations, bindings, routes and pipelines may use
  only tenants it owns. The gate lints pipeline text for tenant headers, `tenant_id` attributes,
  `stage.tenant`, Loki's `__tenant_id__` label and push sources, and in strict mode refuses any
  tenant it does not own or cannot verify (`sys.env`, data-derived values, external `import.*`
  modules). Turning it on is refused, with the list of what to fix, until nothing of the org
  breaks the rule; `AdminService.TenantPreflight` and `shepherd admin tenant-preflight` report
  that list, and with `require_owned` Shepherd refuses to start while it is not empty. The lint is
  defence in depth: a backend's own tenant authentication stays the boundary. (#388)
- **Refused collectors are visible.** Shipped. While a collector's polls are refused, the
  Collectors list shows **REFUSED** in place of its instance status and the collector page shows a
  banner — *Refused — agent token not bound to an organisation* (with a link to Agent Tokens for
  admins), *cluster not allowed* or *role not allowed*. The agent API records the refusal on the
  collector row (migration `0041`, at most once per collector and reason every five minutes, no
  instance row written) and the next poll that passes clears it. (#395)
- **`shepherd dev ensure-org`** (dev-only): creates an organisation idempotently, so a compose
  stack can mint a bound token before any Alloy starts. (#392)

### Fixed

- **The beacon never reported (B-BEACON-SCRAPE).** Shipped. The D6 baseline never delivered a
  sample: it scraped the exporter's remotecfg component path, which Alloy answers with HTTP 400.
  It now scrapes Alloy's root `/metrics`, so `beacon_inventory` fills and reconciliation shows
  observed state. Serve format 4: **every beacon-enabled collector's config changes once (one
  reload)**. `config.server.base_url` must be reachable from the collectors. Exporters inside a
  pipeline's `declare` (such as the Self Monitoring wizard's) were never affected. (#396)
- **The beacon never reported per pipeline.** Shipped. Inventory was keyed on `controller_path`
  alone, which every declare-wrapped pipeline shares, so reconciliation's observed side was
  always empty. The projection now joins `controller_path` and `controller_id`, rolls nested
  module loaders up into their pipeline (unhealthy if any is) and drops the root and bootstrap
  loaders. (B-BEACON-KEY, part of #378, #384)
- **Reconciliation said *In sync* without beacon data.** Shipped. It now says *Observed state
  unknown — no beacon data from this collector yet*, names the beacon env vars and links the
  Collectors docs; *In sync* needs observed data. (#395)
- **Collectors received raw database errors.** Shipped. A new innermost collector.v1 interceptor
  logs any internal error with its detail and answers `unavailable: server temporarily
  unavailable (schema mismatch, likely an upgrade in progress); retry` for a schema mismatch
  (`42P10`, `42703`, `42P01`, `42883`) and `internal: internal error` for anything else. The
  management API's `mapError` no longer sends Postgres text for unique/FK violations and maps
  schema mismatches to `Unavailable`; the OIDC-settings and tenant-route segment paths no longer
  wrap raw errors. (#395)
- **An unbound token's allowlists read "any".** Shipped. Clusters and Roles read
  "— (unbound: refused)"; "any" is shown only for a bound token with empty allowlists. (#395)
- **Collectors could not restart while the database was down.** Shipped. Alloy stops its
  remote-config service when `RegisterCollector` fails at start-up, so a database outage turned
  every restart into a crash loop. Outage-class database errors now answer `Unavailable` (never
  `Unauthenticated`), and for `agent.outage_cache_ttl` (default 60s, `0` turns it off) each
  replica keeps a bounded cache of recently verified tokens (the stored hash, never the secret)
  and of the last config it served each collector: during an outage a known collector is
  acknowledged and re-served that config, everyone else gets `Unavailable`. Revoking or rebinding
  a token, and changing an agent identity, evicts it on the serving replica. The beacon answers
  503 instead of 401 in the same case, so remote_write retries. (#374, #385)
- **A git sync could apply part of a commit.** Shipped. A commit now applies whole or not at all:
  any failing file (Stage 1/2, ownership, a name clash, the dry run, role enforcement) or a
  tripped prune guard writes nothing, the link shows `error` (or `warning` for a guard) naming up
  to five failing files, and the collector keeps serving the previous commit. The commit is
  dry-run once as one merged config for the link's collector, with role enforcement and the D6
  baseline; an error already present before the commit applies with a `warning` naming the
  already-broken pipelines, but a check that could not complete refuses it. Sync audit rows carry
  `commit`, `git_path` and `repo_link_id`, and only the link's collector is recomputed.
  (B-GITSYNC-ATOMIC, #373)
- **Collector instance ids were not bound to an org.** Shipped. Any valid agent token could rebind
  another org's instance id through `GetConfig`, and `UnregisterCollector` had no org check.
  Instances are now keyed per collector (migration `0036`), the instance row is written only after
  the org check, a poll clears `unregistered_at`, and an OIDC-bound or mode-2 caller unregisters
  only its own org's rows. New metric `shepherd_agent_refused_total{reason}`, with rate-limited
  refusal logs. (B-AGENT-INSTANCE, #370)
- **A failed recompute left no audit trail.** Shipped. Both serve paths log at Error, count
  `shepherd_serve_recompute_failures_total`, keep the previous entry and write one
  `serve.recompute_failed` audit row per collector and generation (migration `0035`). Stage 3
  validates the merged config with the D6 baseline appended — the bytes that are served.
  (B-SERVE-AUDIT, #367)
- **A beacon-disabled collector's config flipped between two versions.** Shipped. The eager
  recompute paths appended the beacon baseline and the lazy path did not; one derivation
  (`serve.BeaconBaseline`) now feeds every path. (#372)
- **Saving a pipeline in a large org could exceed the Stage 3 budget.** Shipped. Stage 3 now
  validates only collectors the old or new matchers select, once per distinct merged config, and
  reports a failure against every cluster/role that shares it; the budget is the chart value
  `config.validate.stage3_timeout`. (#379)
- **Restoring a revision switched a live pipeline off.** Shipped. A restore now keeps the
  pipeline's current enabled state; an enabled pipeline's restore still passes Stage 3 first.
  (#377, #383)
- **A pipeline with pathologically deep nesting could crash the server.** Shipped. Such config is
  refused at Stage 1: every parse goes through one guarded entry point that refuses nesting over
  512 levels, expression chains over 4096 links and parsed trees deeper than 1024. (#388)
- **A small visual graph could expand to gigabytes of rendered text.** Shipped. Render output is
  bounded at 1 MiB while it is written (`output_too_large`), duplicate edges are refused
  (`duplicate_edge`), labels and component names over 256 bytes are refused, diagnostics are
  capped, and the quadratic steps in the render sort and the graph parser are gone. Rendered bytes
  are unchanged for every valid graph. (#391, #393)
- **Request sizes were bounded only for collectors.** Shipped. Management-API requests are capped
  at 4 MiB, pipeline contents at 1 MiB on every write and on every RPC that takes Alloy text or a
  graph, and `gitsync.max_file_bytes` at 1 MiB; collector requests are bounded too. (#370, #388)
- **Deleting a repository link recomputed every dirty collector in the org**, not just the link's;
  it now recomputes that collector only, and the org's served-config and revision views refresh.
  (#371, #364)
- **Serve path internals and small fixes:** one shared serve-cache write (`serve.Store`) for both
  paths; a component schema that fails to load is fatal at boot instead of serving without role
  enforcement; errors wrapped with context in tenant-route apply and destination encoding; the
  graph view builds its module index once per graph; the database docs page says Shepherd calls
  the Kubernetes API when the receiver tier applies tenant routes. (#364, #366, #367)

### Security

- **The per-IP local sign-in throttle could be bypassed with spoofed forwarding headers
  (`True-Client-IP`, `X-Real-IP`, `X-Forwarded-For`).** Shipped. The server's middleware chain
  included chi's `middleware.RealIP` (deprecated upstream for this reason: GHSA-3fxj-6jh8-hvhx,
  GHSA-rjr7-jggh-pgcp, GHSA-9g5q-2w5x-hmxf), which replaced the request's source address with
  whatever the client put in any of those headers. The per-IP bucket on
  `POST /api/auth/local/login` (60 attempts, then 1 a second) is keyed on that address, so a
  client sending a different value on every request got a fresh bucket each time and could guess
  passwords across many usernames without ever being throttled per IP. The per-username bucket
  (10 attempts, then about 1 every six seconds) was unaffected, so guessing against any one
  account stayed limited. OIDC sign-in and the API token paths do not use the per-IP throttle.

  Shepherd no longer trusts forwarding headers from just anyone. The client address is the
  direct TCP peer unless that peer is listed in the new **`server.trusted_proxies`** setting
  (`config.server.trusted_proxies` in the chart; CIDRs; default empty). Only then is it taken
  from `X-Forwarded-For`, read right to left past the trusted hops; `X-Real-IP` and
  `True-Client-IP` are never read, and `r.RemoteAddr` is never rewritten. **With

  default `proxy-real-ip-cidr`, NGF `rewriteClientIP`), and ideally a NetworkPolicy so only the
  proxy can reach Shepherd. `/0`, IPv4 prefixes shorter than `/8` and IPv6 prefixes shorter than
  `/16` are rejected at startup. See `deploy/helm/shepherd/UPGRADING.md` (0.21.x → 0.22.0) and

### Added

- **Destination tenant IDs are sent (#261).** A destination's tenant ID was stored and never
  rendered. Every wizard writer now sends it: a `headers = { "X-Scope-OrgID" = … }` entry on

  generated, and `CreateOrg` / `SetOrgTenantID` refuse a tenant ID another organisation's

  Secret, key `ca.crt` or one you name), present a client certificate (a `kubernetes.io/tls`

### Fixed

- **The validation gate refuses two wiring mistakes that `alloy validate` accepts and Alloy
  refuses at load (#233).** `alloy validate` does not evaluate references between components,
  so it passed `targets = [discovery.kubernetes.pods.targets]`. That wire is a list of lists and
  fails on every collector with `conversion from '[]discovery.Target' is not supported`. It also
  passed `forward_to = prometheus.remote_write.x.receiver`, a single receiver where a list is
  required. Stage 2 now also checks each wire against the component schema and refuses both, with
  the line, column and the fix ("drop the brackets" / "wrap it in brackets"). The check runs on
  every path that validates config: UI and API saves, the editor's Validate, wizard and visual
  saves, the Stage 3 dry-run, git sync, sandbox runs and `shepherd validate`. It runs even when no
  Alloy binary is configured. It is deliberately narrow and flags only references it can type with
  certainty. Run over every Alloy config in the repository (goldens, seeds, fixtures, docs), it
  finds nothing new. **Upgrade note:** stored pipelines are not re-checked on upgrade. A pipeline
  already written in the bracketed form is refused at its next save or sync. Stage 3 validates
  each affected collector's whole merged config, so until it is fixed it also blocks saves of other
  pipelines that land on the same collectors. Those collectors already fail to load it.

- **A failing collector no longer turns APPLIED when Shepherd serves it a new config.** v0.13.0's
  fix (#115) covered a rejected config followed by silent polls, but Alloy re-sends a status only
  when the error *message* changes: when a label edit or any other change served a new config that
  failed the same way, the agent stayed silent and Shepherd read that as recovery. A status-less
  poll now keeps the last reported outcome (and follows the new config); it means APPLIED only when
  Alloy proves a load by sending its effective config.

- **A replaced Alloy pod's FAILED instance no longer lingers as FAILED for a day.** "Inactive" is
  now derived from an instance's last check-in when it is read (`agent.inactive_after`), instead of
  being written over its status by the lifecycle sweeper. A stale instance shows `inactive`
  whatever it last reported — on Kubernetes every Alloy restart registers a new instance, so the
  dead pod's row turns inactive while the new one carries the collector's status — and its
  reported outcome is kept, so a failing collector that comes back still shows FAILED rather than
  APPLIED. `shepherd_active_collectors` counts the same way; with `agent.inactive_after` unset
  nothing is ever inactive. Migration `0029` clears the old `inactive` markers (to "nothing
  reported", what a reconnect used to turn them into); no action needed. (#237)

- **Recomputing an unchanged config no longer makes the fleet reload.** The served config's
  header carried the time it was generated (`// Generated by Shepherd prod at <time>`), and that
  line is part of the hashed content, so every recompute — a label edit, any change that marks
  collectors' configs for recompute — gave every affected collector a new hash although nothing
  else changed, and each one re-fetched and reloaded. The header is now `// Generated by Shepherd
  prod`: the served bytes and their hash depend only on the merged configuration. **On upgrade**
  every collector's served hash changes once (the header line changed), so the fleet re-fetches
  and reloads one time; nothing to do. (#213)

- **The chart's server Services, PDB and NetworkPolicies no longer select the simulator or
  receiver pods.** They selected on the release-wide `app.kubernetes.io/name`/`instance` labels,

  minutes.** The setting has no server default (the chart sets it), and the sweeper read an unset

  missing status was promoted to APPLIED — a failing collector read APPLIED within five minutes on
  any install without the chart. Unset now turns the delete off. Chart installs were not affected.
  (#230)

- **Git sync runs on one replica at a time.** Each replica ran its own sync loop, so a new commit
  seen by both at once could be synced twice, writing duplicate revisions and audit rows. Passes
  now take a Postgres advisory lock, as tenant-route apply already did. (#210)

- **Every mutating action is audited.** Fourteen write procedures wrote no audit row — editing or

- **Restoring a revision says when it changes the pipeline's enabled state,** and audits the flip

- **Reconciliation no longer says "In sync" for a FAILED collector.** (#198)

- **The editor says when `alloy validate` did not run.** With no Alloy binary configured, Stage 2

  writes are org-admin. The segment is minted server-side and is an identifier, not an authorizer —
  the page says so, since rate limiting belongs at the gateway. Creating a route needs the org to
  have a tenant identity (an app admin sets it on Organisations); the page surfaces that
  precondition. Storage/lifecycle surface only — applying routes to Kubernetes is the receiver tier.
- **Service accounts have a UI.** A new org-scoped Service accounts page (list, create, revoke)

- **Collector inventory labels.** Attach free-form key/value labels to a collector from the UI (the
  Collectors list and a collector's detail page) to filter and group the fleet, without touching the
  Alloy-reported attributes or the labels the merge engine matches pipelines against. Keys normalise

- **`shepherd_build_info` metric.** A constant gauge on `/metrics` whose `version` and `commit`

### Added

### Fixed — found by the first `make dev-kind` bring-up

- **A chart-declared OIDC issuer on a private address could not complete a login.** Discovery

  the discovery document fetched its signing keys through the address-guarded client, so every

- **The dev stack's Alloy agents start only after the chart and the seed.** Alloy's `remotecfg`

### Fixed — served-config header

- **An unparsable matcher vanished from the served header whenever role enforcement ran.** Two
  exclusion lists feed the `// Excluded (n)` header block: pipelines whose matcher does not parse
  and pipelines the role gate removed. The second replaced the first, so on every production
  deployment (a schema registry is always wired) a broken matcher was excluded silently. The lists
  are now appended. Header only; which pipelines are served does not change.
- **The "recompute failure serves previous content" spec had stopped failing the recompute.**
  It relied on a malformed matcher aborting assembly, which the exclusion above turned into a
  successful recompute, so it only passed while both computes landed in the same second (CI run
  34968998790). It now breaks the pipelines table under the recompute and asserts the failure
  counter moved, so a same-second pass cannot hide a non-failure again.
### Fixed — pipeline names in the served header

- **A line break in a pipeline name could take every collector it matched offline.** The served
  config's header writes the pipeline name and the collector display name into `//` comment
  lines; exclusion reasons were already collapsed to one line, names were not. A name with a
  newline ended the comment, the rest became syntax, Stage 1 rejected the assembled output, and
  every matched collector stayed on its previous config. Every string the header interpolates is
  now collapsed to one line, so rows that predate the API check below, Git-sourced pipelines and
  direct writes are covered too.
- **`CreatePipeline` and `UpdatePipeline` refuse names with control or format characters**
  (`InvalidArgument`, "name must not contain control or format characters"). Ordinary Unicode
  letters stay allowed. A name is a label, not a text field; it lands in the served header and in
  audit rows.

## v0.3.5

Chart 0.9.0. **A chart-only release — the application is byte-for-byte v0.3.4.**
It carries a version of its own solely because the chart is published under a
git tag and the release refuses to ship a chart whose `appVersion` does not
match that tag. Nothing in Shepherd itself changed; if you do not deploy with
Helm there is no reason to upgrade.

**Upgrading the chart from 0.8.x needs one manual step.** See below, or
[UPGRADING.md](deploy/helm/shepherd/UPGRADING.md).

### Breaking — one adoption step on the first upgrade

- **The runtime `ConfigMap`, `Secret` and `ServiceAccount` are no longer Helm
  hooks.** They were, to solve an ordering problem: Helm runs every hook before
  any normal resource, so the pre-install migration Job could not otherwise see
  them. That fixed the ordering and cost three things, because Helm does not
  track hook resources in a release:

  - `helm rollback` did not revert them. Rollback runs `pre-rollback` hooks,
    never `pre-upgrade` ones, so the ConfigMap stayed at the *new* content while
    the Deployment went back to the *old* image — a config/code mismatch after
    the exact operation people run when an upgrade has gone wrong.
  - `helm uninstall` left them in the namespace, including — when `secrets:` was
    used — a Secret holding the database URL and the encryption key.
  - Setting `migrations.job.enabled: false` made the release unupgradable: the
    same objects became tracked resources Helm could not adopt.

  The migration Job now gets its own short-lived `<release>-migrate` copies,
  deleted when the migration succeeds, and the runtime objects are ordinary
  tracked resources.

  **What you must do:** hook-created objects carry no Helm ownership metadata,
  so the first upgrade cannot adopt them and stops. The chart detects this and
  prints the exact commands rather than letting Helm fail one object at a time
  with `invalid ownership metadata`. Running them changes no data, restarts
  nothing, and is safe while Shepherd is serving.

  Note the consequence of the fix: `helm uninstall` now **does** remove the
  chart-rendered `<release>-secrets`. If you relied on the old leave-behind to
  preserve the encryption key across an uninstall/reinstall, copy it out first.

### Fixed — data loss under GitOps

- **The guards protecting the database and the encryption key fail open under
  Argo CD, Flux and `helm template | kubectl apply`.** v0.3.4 stopped `helm
  upgrade` destroying the CloudNativePG `Cluster` by rendering it only when it
  does not already exist. That guard uses `lookup`, which needs a live cluster
  connection — and a tool that renders the chart offline and applies the output
  has none. There the check silently passes, the `Cluster` is emitted on every
  sync, and Argo CD maps `helm.sh/hook: pre-install,pre-upgrade` onto a PreSync
  hook whose default policy is `BeforeHookCreation`: delete, then recreate.
  CloudNativePG cascades that to the PVCs, the migration Job migrates a fresh
  empty database, and the sync reports success.

  The same shape applies to the `ExternalSecret`, which regenerates the
  encryption key that **cannot** be rotated.

  New `cnpg.render` and `externalSecrets.render` (`auto` | `always` | `never`)
  make the decision explicit where `lookup` cannot. **If you deploy this chart
  with Argo CD or Flux, set both to `never` once the database and secret
  exist.** `auto` remains the default and is correct under the `helm` CLI.

### Fixed — installs that could never succeed

- **The migration Job was rejected outright by any namespace enforcing the
  `restricted` Pod Security Standard.** It carried only a container-level
  `securityContext`; `runAsNonRoot`, `runAsUser` and `seccompProfile` appeared
  nowhere. Because the Job is a pre-install hook, that is not a failed migration
  but a failed *install* — while the Deployment it was migrating for would have
  been admitted. Verified against a real cluster: `pods "shepherd-migrate-…" is
  forbidden: violates PodSecurity "restricted:latest": runAsNonRoot != true,
  seccompProfile …`, a `FailedCreate` loop that never produces a pod.
- **The migration Job ignored `image.pullSecrets`.** Any private-registry
  install with migrations enabled — the default — died in `ImagePullBackOff` at
  the pre-install hook, surfacing minutes later as a `--wait` timeout before a
  single tracked resource existed.
- **`autoscaling.enabled` rendered an HPA that could never scale.** A CPU
  utilization target is a percentage *of the request*, and `resources` is `{}`
  by default, so the two defaults together produced an autoscaler stuck in
  `FailedGetResourceMetric` — indistinguishable from one that had decided not to
  scale. The chart now refuses to install without `resources.requests.cpu`.
- **A wildcard ingress host failed the whole render.** `*.example.com` starts
  with the YAML alias character and the host was unquoted, so the error named a
  line number rather than the host.

### Fixed — values that did the opposite of what they said

- **`cnpg.enabled: "false"` provisioned a database.** Go templates read any
  non-empty string as true, so quoting a boolean turned the feature *on*. The
  same applied to `metrics.enabled`, `migrations.job.enabled` and
  `externalSecrets.enabled`; `values.schema.json` caught it only for `route` and
  `ingress`. The schema now covers every value block and rejects a quoted
  boolean with the offending path named.
- **Misspelt keys were silently ignored.** `simulater:`, `replicaCount:`,
  `config.tracing.endpont:` — all accepted, all doing nothing, with no
  indication the value you set went nowhere. Unknown keys are now rejected.
  Closed sets are enforced too, including `config.validate.stability_level`,
  which is passed verbatim to `alloy --stability.level=` and whose typo failed
  every config validation in-cluster with nothing catching it at install.

### Fixed — chart correctness

- **The `PodDisruptionBudget` keyed off `.Values.replicas`**, which is not the
  replica count once an HPA owns it — the Deployment stops rendering it. With
  `autoscaling.minReplicas: 1` and the default `replicas: 2` that produced a
  `minAvailable: 1` budget which deadlocks every node drain the moment the
  autoscaler scales to one pod. It now follows the effective minimum.
- **Rotating a value in `secrets:` did not restart anything.** Environment
  variables are read once at container start, so pods kept the old credential
  until an unrelated rollout. A `checksum/secret` annotation (a hash, never the
  value) now rolls them.
- **`NOTES.txt` printed commands that do not work**: a collector URL hardcoded
  to `http://shepherd:8080`, wrong for any release not named `shepherd` and
  ignoring `service.port`; an ingress the URL branch never consulted; a
  `port-forward` instruction given even for `service.type: NodePort`; and
  multiple route hostnames concatenated into one unusable string.

### Added

- **`serviceAccount.create` / `.name` / `.annotations`** — the ServiceAccount
  name was hardcoded, so there was nowhere to put an EKS IRSA role ARN or a GKE
  Workload Identity binding, which is how a pod reaches RDS or Cloud SQL without
  a static credential.
- **`migrations.job.resources`** — a namespace with a `ResourceQuota` or
  `LimitRange` requiring declared resources refuses the migration pod, and a
  refused hook pod fails the whole install.
- **`kubeVersion: ">=1.25.0-0"`** in `Chart.yaml`. Note this also affects
  offline rendering: `helm template` takes its Kubernetes version from the
  `helm` binary's own defaults, so a sufficiently old `helm` will refuse to
  render the chart with no cluster involved.
- Pod-level `automountServiceAccountToken: false` on both workloads.

### Fixed — test coverage that was never there

- **`ingress.yaml`, `hpa.yaml` and the main chart's `networkpolicy.yaml` had
  never been rendered by anything** — no `ci/` values file and no test. The
  full-values profile enables `route`, and the schema forbids `route` and
  `ingress` together, so a template error in any of the three passed CI and
  would have surfaced on somebody's cluster. `ci/ingress-values.yaml` now covers
  them, and `make helm-lint` renders the pristine defaults too, which every
  other `ci/` file overrides.

### Documentation

- The pages explaining why the database and the encryption key are safe credited
  the protection to hook status and to `refreshInterval: "0"` /
  `deletionPolicy: Retain`. Under a GitOps tool, hook status is how the database
  gets deleted, and the chart's own comment notes those two settings "do nothing
  if Helm DELETES and RECREATES it". Both pages now describe the real guard and
  its GitOps failure mode.
- Nothing on the site covered deploying the chart with Argo CD or Flux, and the
  reader looking for it landed on the GitOps page — which is about Shepherd's
  git *pipeline* sync. That page now disambiguates and links to both `render`
  values.
- The documented upgrade command had no mention of the adoption step above. Adds
  a high-availability section that the quickstart had been advertising all along
  and which did not exist, and corrects the ingress example, which took a bare
  string where the chart wants `hosts[].host` with a list of paths.

## v0.3.4

Chart 0.8.2. A full-application review, fixed. **If you enabled
`cnpg.enabled` on chart 0.8.0 or 0.8.1, upgrade before your next
`helm upgrade`** — see the first entry.

### Fixed — data loss

- **`helm upgrade` destroyed the database when `cnpg.enabled` was set**
  (charts 0.8.0 and 0.8.1). The CloudNativePG `Cluster` renders as a Helm hook,
  and Helm's documented default hook-delete-policy — applied precisely when the
  annotation is *omitted* — is `before-hook-creation`. The chart's comments
  claimed the opposite, so every upgrade deleted the live Cluster and
  CloudNativePG cascaded that to the PVCs. Measured by removing the fix and
  running the Kubernetes suite: the upgrade hung for 916 seconds and failed with
  `Deployment/shepherd not ready ... Available: 0/1`, the application unable to
  start because its database had been removed underneath it.

  The same shape applied to the `ExternalSecret`, which regenerated the
  encryption key that **cannot** be rotated — silently orphaning every git
  credential and OIDC client secret already stored.

  The chart now renders both only when they do not already exist, so an upgrade
  leaves them untouched. A hook absent from the manifest is never processed.
  There is no annotation that expresses "never delete", which is why this is a
  render guard rather than a policy.

  **If you are on 0.8.0 or 0.8.1 with `cnpg.enabled`:** upgrade to 0.8.2 *before*
  running any other `helm upgrade`. Back up your database first. Charts 0.8.0
  and 0.8.1 should be treated as withdrawn for that configuration.

### Fixed — cross-org access

- **Four by-id handlers acted on ids without checking they belonged to the
  requesting org.** Neither the Connect interceptor nor the REST middleware can
  do that for them: both authorize the org *named in the request*, which proves
  the caller holds a role there and says nothing about the id passed alongside
  it. A reader in one org could read another org's collectors and their full
  served config — destination URLs, tenant ids, and any credentials embedded in
  pipeline contents. An admin could grant their own group standing access to
  another org's collector, or delete another org's git credentials and repo
  links.
- **The reader-floor fallback in `authorizeOrgAccess` was not org-scoped.** It
  asked "does this session hold a collector assignment *anywhere*", so one
  assignment in one org cleared the reader floor in *every* org — invisibly,
  because `/api/me` builds its org list from group matches and never showed the
  extra orgs.

### Fixed — revocation

- **Disabling or demoting an account did not end its sessions.** `is_app_admin`
  is copied into the session row at login and `disabled` was only checked at
  login, so a revoked administrator kept full app-admin until the cookie expired
  — up to 8 hours. The last-admin guard exists to control exactly that removal;
  it now takes effect immediately.

### Fixed — served configuration

- **GitOps pipelines were silently dropped from served config.** Both management
  API merge paths used the query that omits `repo_link_collector_id`, and a git
  pipeline matches *solely* by that field. Stage 3 therefore validated a merged
  config no collector would receive, and the eager recompute wrote serve caches
  without the org's GitOps pipelines and marked them clean, so the correct path
  never ran again.
- **One unparsable matcher froze configuration serving for a whole
  organisation**, and a newly-claimed collector was served an *empty* config,
  wiping what it was already running. Matchers are now parsed when saved
  (the previous check was unreachable), and an unparsable one excludes only
  itself.
- **`UpdatePipeline` skipped stage 3**, so the merged dry-run ran only when
  enabling a pipeline, not when editing one that was already enabled.
- **GitOps could take over a same-named UI pipeline** — replacing its contents
  while keeping its matchers, deploying repo content to every collector those
  matchers selected.

### Fixed — chart and release

- `helm upgrade --reuse-values` from a release older than the `cnpg` /
  `externalSecrets` / `simulator` keys failed to render at all.
- `networkPolicy.enabled` silently blocked every metrics scrape, including the
  ServiceMonitor the same values file recommends.
- The HPA and `spec.replicas` fought: every upgrade snapped scale back.
- `externalSecrets.enabled` without a database URL now fails at render with an
  explanation, instead of a migration Job that dies on connect minutes later.
- Release consistency guards run *before* anything is published, rather than
  after images and the GitHub release are already public.

### Fixed — UI

- **Org editors could not author anything.** The role shipped server-side in
  v0.3.0 and the UI still checked for `admin` alone, so the role that exists to
  author pipelines got a read-only page and a locked editor.
- **`javascript:` destination URLs reached an `href`**, and an unparsable one

- The pipeline editor discarded unsaved edits whenever a background refetch

## v0.3.2

Chart 0.8.0. No application changes: this release is the chart learning to
provision the two things every install previously had to arrange by hand.

### Added

- **`cnpg.enabled`: let the chart provision the database.** With the
  [CloudNativePG](https://cloudnative-pg.io/) operator installed, the chart
  renders a `postgresql.cnpg.io/v1` Cluster and wires Shepherd's database URL to
  the `uri` key of the `<cluster>-app` Secret the operator generates &mdash; so
  no connection string is written anywhere. Off by default, and bringing your
  own RDS or Postgres remains the default path, unchanged.

  The Cluster renders as a `pre-install` hook so it exists before migrations
  run, and therefore is not deleted by `helm uninstall`: hook resources are not
  tracked in the release, which for the thing holding all the data is the right
  way round. `migrations.job.backoffLimit` is now explicit, because on a first
  install the migration Job races a database that is still initialising and has
  to retry until it does not.

- **`externalSecrets.enabled`: let the cluster generate the bootstrap secrets.**
  With the [External Secrets Operator](https://external-secrets.io/) installed,
  the chart renders two `Password` generators and an `ExternalSecret` producing
  the encryption key and the first administrator's password, so neither ever
  passes through a shell, a values file, or terminal history. No `SecretStore`
  is needed; a generator is the source.

  `refreshInterval` is `"0"` and `deletionPolicy` is `Retain`, and both are
  asserted by the chart tests rather than left as comments. Regenerating the
  encryption key would leave every git credential and OIDC client secret
  already in the database undecryptable, and nothing would report it at the
  moment it happened &mdash; the failure looks exactly like Shepherd forgetting
  your credentials.

  It refuses to render alongside `existingSecret` or an inline `secrets:` block
  rather than producing two competing definitions of the same Secret.

- **Docs: Database and Secrets pages**, covering both choices for each, and a
  generated [Helm values](https://procoduck.github.io/shepherd/docs/helm-values.html)
  reference that cannot fall behind the chart.

## v0.3.0

Local accounts become a first-class way to run Shepherd, a third org role
splits authoring from re-pointing telemetry, and teams stop requiring an

### Breaking

- **`auth.local_admin.*` is gone.** The single hardcoded break-glass account it
  configured has been replaced by full local user management, so the config
  block no longer exists. **Remove it from your values file.** Configuration is
  decoded leniently, so a block that is left in place is ignored in silence
  rather than rejected — nothing warns you, and the account it describes will
  not exist. Replace it with
  `SHEPHERD_BOOTSTRAP_ADMIN_LOGIN` / `SHEPHERD_BOOTSTRAP_ADMIN_PASSWORD`, which

  the database, so `SHEPHERD_AUTH_LOCAL_ADMIN_PASSWORD_HASH` is no longer read.
- **`/api/me` reports an org role of `viewer`, not `reader`.** The three org
  roles now have one vocabulary — `admin`, `editor`, `viewer` — across both the
  API and the UI. The `reader_group_id` column and chart key keep their names:
  renaming them would break every chart and secret already deployed. Only the
  reported role string changed.

### Shipped

- **Local user management.** Shepherd runs with no identity provider at all.
  Any number of local accounts, each with an app-admin flag and a per-org role,
  managed at **Admin → Users**. This is *additive*: group-derived identity from
  OIDC is unchanged, and the two coexist — a deployment can use either or both.
  A local session is judged on its stored membership alone and an OIDC session
  on its groups claim alone, so "why does this person have access" always has a
  single answer.
- **An org editor role.** Authoring a pipeline and re-pointing where an org's
  telemetry ships used to be the same permission. An editor may write what the
  org *runs* — pipelines, wizards, the visual builder, simulations — while what
  the org *is* (destinations, tenant routes, git credentials, teams, service
  accounts) stays with the org admin. Reachable from an IdP group
  (`editor_group_id`, set at **Admin → Orgs**) or from a local user's org role.
- **Teams have a UI, and can hold explicit members.** A team previously bound
  to an IdP group and nothing else, which meant a deployment without an IdP
  could not use team-scoped write at all. Teams now take local users directly,
  and the **Teams** page shows which source each team draws its members from.
  A group-backed team shows no roster on purpose: membership lives in a token
  claim, so there is nothing to list.

### Fixed

- **An org admin who signed in locally could not write any pipeline.** The
  ownership check matched the org's admin group inline against the session's
  groups claim; a local session has none, so it was refused both owned and
  unowned pipelines. It now resolves the role the same way every other
  authorization decision does.
- **An unrecognised `minRole` on a route no longer defaults to reader.** With
  a third role that default became a silent privilege widening — the route
  keeps serving, just to more people than intended. It now fails while routes
  are registered.

## v0.2.0

Shepherd instruments itself, and several things that looked like they worked did
not. The minor bump rather than a patch is about the chart: `metrics.enabled`
defaults on, so an existing `helm upgrade` now renders a Service and a container
port it did not have before, and operators should know that before they upgrade.

### Added

- **Shepherd instruments itself.** The `/metrics` endpoint previously exposed
  four series, of which one was wrong. It now covers the serving paths:
  - `shepherd_http_requests_total` and `shepherd_http_request_duration_seconds`
    for every HTTP request, labelled by chi ROUTE PATTERN rather than URL — a
    per-id label would mint a time series per org and per pipeline, which is
    how a metrics endpoint takes down the Prometheus scraping it. Unmatched
    paths collapse to one `other` series so an unauthenticated scanner cannot
    create series at will.
  - `shepherd_rpc_requests_total` and `shepherd_rpc_duration_seconds` for every
    Connect RPC on both the agent and management surfaces, labelled by
    procedure and result code. A failed call is counted under its code, because
    an auth-failure spike is exactly what a graph is for.
- **Chart support for both.** `metrics.serviceMonitor.*` gained `interval`,
  `scrapeTimeout`, `relabelings` and `metricRelabelings`; `config.tracing`
  carries an explicit `enabled` switch plus the OTLP endpoint, protocol, TLS
  and sampling settings. Enabling tracing without an endpoint is reported as a
  misconfiguration in the logs rather than silently doing nothing — an empty
  trace backend with no explanation is the worst way to discover a typo.
- **OpenTelemetry tracing**, off unless `tracing.enabled` is set — and off
  means no provider, no exporter, and a no-op tracer, which is what makes
  instrumenting the hot agent path defensible. Server spans for HTTP requests
  and Connect RPCs, with inbound trace context honoured so a call that crossed
  from the UI into the API is one trace rather than two. Health probes, the
  metrics scrape, and static assets are never traced.

### Fixed

- **Four of the six declared metrics were never observed**, so `/metrics` was
  reporting on almost nothing:
  - `shepherd_active_collectors` was declared, never set, and therefore
    reported **0 while collectors were actively polling**. A gauge that is
    always zero is worse than a missing one: it cannot be alerted on, and an
    alert written against it looks like coverage while being incapable of
    firing. It is now published by the sweeper, including once at startup —
    waiting for the 5m tick would have left it lying for five minutes after
    every rollout.
  - `shepherd_getconfig_duration_seconds`, `shepherd_gitsync_total` and
    `shepherd_validation_total` never appeared in `/metrics` at all: a labelled
    metric does not materialise until something observes it. There was no
    latency histogram, no git-sync outcome counter, and no count of the
    three-stage validation gate — the product's core safety mechanism.
  - Stage 2 is counted as `skipped` rather than `valid` when no Alloy binary is
    configured. That distinction is the v0.0.2 bug made visible: a deployment
    where `alloy validate` cannot run reports success while validating nothing,
    and now says so on a dashboard.
- `shepherd_table_rows` published `-1`, which is Postgres's `reltuples` value
  for a table it has never analyzed. The series is now omitted instead, since
  "unknown" is what it means.
- **The chart's ServiceMonitor scraped a port that has never served metrics.**
  It pointed at `port: http` (`:8080`) with `path: /metrics`, but metrics live
  on their own listener and `/metrics` on the main port is explicitly
  404-guarded — so `metrics.serviceMonitor.enabled=true` produced a permanently
  failing Prometheus target and no metrics at all. There was also no container
  port and no Service for the metrics listener, so there had never been
  anything to scrape. The Deployment now declares a `metrics` port, a
  dedicated **ClusterIP** Service fronts it (deliberately not a port on the
  main Service, which becomes externally reachable the moment an operator
  chooses `LoadBalancer` or `NodePort`), and the ServiceMonitor selects that
  Service by component label. All three derive the port number from
  `config.server.metrics_listen`, so they cannot drift apart again. Chart
  render tests assert each of these against real `helm template` output.
- **The access log was emitted at `Debug`**, so a default `info` deployment
  produced no per-request record at all — a failing API returned 500s with
  nothing in the logs. Server errors now log at `Error`, client errors at
  `Warn`, and the successful bulk stays at `Debug` so continuous collector
  polling does not drown the log; volume and latency are the metrics' job.

- **Audit entries for single sign-on were written where nobody could read them.**
  Platform-level events carry no `org_id` (SSO configuration belongs to no org),
  every caller of the audit query passes an org, and `org_id = $1` silently
  excluded them — so the trail for repointing the identity provider, which the
  code itself calls the highest-leverage write in the product, could only be
  read with `psql`. App admins now see platform events folded into whichever
  org they are viewing; an org admin's view is unchanged, because these are
  platform decisions rather than anything about their org. Found by walking the
  running app, not by a test: the tests asserted the row reached `audit_log`,
  which is exactly the assertion that let this ship.

### Upgrading

- **The chart renders two new things.** `metrics.enabled` defaults to `true`, so
  `helm upgrade` adds a `<release>-metrics` **ClusterIP** Service and a `metrics`
  container port (`:9090` by default, from `config.server.metrics_listen`). The
  metrics listener was already running — it simply had nothing in front of it.
  Neither is externally reachable; set `metrics.enabled: false` to opt out.
- **Nothing else changes behaviour.** Tracing is off unless you turn it on,
  the new metrics are observational, and the access-log change only makes
  failures visible at the default log level.
- **If you had `metrics.serviceMonitor.enabled: true`, it was scraping a 404**
  and is now scraping real metrics — expect series to appear where a target had
  been failing.

- **Single sign-on is now documented for users**, in the README and on the docs

## v0.1.0

A feature release. Single sign-on can now be configured from the admin UI, and against providers
other than Microsoft Entra ID. The minor bump rather than another 0.0.x is deliberate: this
changes how authentication is configured, and two existing behaviours change with it — read
"Changed" below before upgrading an Entra deployment.

### Shipped

- **OIDC is configurable from the UI, for ten common providers.** `oidc.issuer` decides where
  configuration comes from. Set it in the chart and the chart wins, with the UI showing the values
  read-only — a cluster whose identity provider is declared in git must not be re-pointed by
  whoever holds an app-admin session. Leave it unset and an app admin configures a provider at
  **Admin → Single sign-on**, with the local-admin break-glass account as the bootstrap path.
  Presets for Entra, Okta, Google, Auth0, Keycloak, AWS Cognito, GitLab, authentik, OneLogin, and
  generic, each carrying the claim names that provider actually emits plus a note on what must be
  configured *in the IdP* for group membership to arrive at all — the likeliest way to get this
  wrong, because it fails silently as an empty group list.
- **Saving takes effect without a restart.** The discovered provider lives behind an atomic
  pointer; other replicas converge within 30s. Discovery runs *before* the write when enabling, so
  a provider that cannot discover is never stored as live — the admin who would have to fix it may
  be relying on that same login page.
- **Claim mapping is per-provider configuration**, not constants: subject, email, name, and groups
  claim names are all settable. The groups reader accepts every shape providers use (JSON array,
  bare string, space-separated). Group *values* are matched against the app-admin list and each
  org's admin/reader group, so for a non-Entra provider those hold whatever your IdP emits —
  usually a group name or path, not a GUID.
- **A "Test connection" probe** reports the discovered issuer and endpoints before you enable
  sign-in. It checks discovery only: the client ID, secret, and redirect URL are not exercised
  until someone actually signs in, and the UI says so.
- The client secret is AES-256-GCM encrypted at rest and never returned by the API — the settings
  form is told only whether one is stored.

### Changed

Both of these affect existing Entra deployments configured through the chart. Neither requires a
config change, but both are worth knowing before you upgrade.

- **A failed Microsoft Graph lookup now falls back to the ID token's groups claim.** Previously a
  Graph outage, a revoked `GroupMember.Read.All` consent, or a 403 produced *no* groups, which
  silently stripped every administrator of access until Graph recovered. The claim is signed by
  the same provider so it cannot be forged, but it is **not the same set** — claim scope is
  configured per app registration ("all groups" vs "groups assigned to the application"), and
  AD-synced groups may emit `sAMAccountName` rather than GUIDs. A deployment that wants the old
  all-or-nothing behaviour should leave the groups claim unmapped in its app registration.
- **`oidc.scopes` gained a default of `[openid, profile, email]`.** A deployment configured purely
  through `SHEPHERD_OIDC_*` environment variables previously arrived with an empty scope list,
  which was then filled in from the Entra preset — silently adding `GroupMember.Read.All` to the
  authorize request. That scope needs admin consent in a real tenant, so this could turn a working
  login into `AADSTS65001`. Set `oidc.scopes` explicitly if you rely on the Graph lookup.
- **`auth.session_ttl` gained a default of `8h`**, matching the chart. A zero TTL expires every
  session the instant it is created; that was unreachable while authentication required chart
  config, and became reachable once OIDC could be enabled in a deployment whose chart set no
  `auth` block.

### Security

These were found by an adversarial review of the feature before it shipped, not in the field. They
are listed because the code is new, not because any released version was affected.

- **OIDC discovery is a constrained fetch.** It is the one place an authenticated user picks a URL
  the *server* then retrieves, and app admin is an application role, not cluster-admin. Discovery
  now runs under a 10s timeout, through a dialer that rejects loopback, private, link-local, and
  CGNAT addresses *after* DNS resolution (so a hostname resolving to `169.254.169.254`, and DNS
  rebinding, are both covered), and follows only `https` redirects. Discovery errors carry the
  status code and never the response body — `go-oidc`'s own error embeds the whole body, which
  would have made the connection test readable as well as probeable.
- **`graph.base_url` is pinned to Microsoft's own Graph hosts** (global plus the sovereign clouds).
  The signing-in user's delegated access token is sent to it as a bearer credential, so an
  unconstrained value would let an app admin collect every user's token on their next login.
- **The redirect URL must be exactly `/auth/callback`.** A suffix check would also have accepted
  `/evil/auth/callback`.
- **Background settings refreshes run on a context detached from the request.** The refresh spends
  its 30s backoff before it attempts anything, so inheriting request cancellation let an
  unauthenticated caller who aborts `/auth/methods` every 30s keep a replica from ever activating
  OIDC.

### Fixed

- `make fmt` no longer reformats the repository into a state `make lint` rejects. It shelled out to
  the standalone `gofumpt` binary, which decides an import is local by looking for a dot in its
  first path segment; this module is plain `shepherd`, so `shepherd/internal/...` was classified as
  stdlib and merged into the std import group, which `gci` then refused. `golangci-lint fmt` runs
  both formatters with the right configuration and was always the whole job.

## v0.0.3

A fix release. v0.0.2's shipped image could not run `alloy validate` at all, and a manual
walkthrough of a real deployment found that plus three more gaps that the test suite could not.
No new features; nothing that was gated in v0.0.2 has been ungated.

### Fixed

- **`alloy validate` (Stage 2 of the validation gate) was dead in every container, the released
  v0.0.2 image included.** The image bundles the `alloy` binary so it can validate pipeline config
  before serving it, and `alloy` is dynamically linked — but the base was `distroless/static`,
  which carries no dynamic loader, so the binary was present and unrunnable. Every pipeline save in
  a Helm deployment failed Stage 2; dev and compose stacks silently *skipped* it (they leave the
  binary path empty), which is why no test caught it. Fixed by moving to `distroless/base-nossl`,
  and the `check-alloy-runnable` macro (a Makefile `define`, not a target — invoked from
  `docker-build-local`, not run standalone) now fails the build if it regresses. **This is the
  reason to upgrade.**
- **Five of six wizards were absent from the running product.** Their packages were never imported,
  so they never registered; `ListWizards` returned one. Now all six are registered and reachable,
  and the wizard gallery/runner render whatever the backend serves rather than a hardcoded list.
- **A machine actor's on-behalf-of attribution was not shown in the audit UI.** The value was
  stored and returned but never rendered, so a human reading the audit log could not see who
  authorised a machine's write. The audit table now has an "On behalf of" column.
- **Destination and binding writes were not audited**, and a binding's `tenant_id` was not
  validated. Both fixed — a binding decides which tenant a team's telemetry ships under, so it is
  audit-worthy and its tenant id now goes through the same rule routes use.

### Also

- Images drop OpenSSL (`base-nossl`, not `base`): nothing in either binary links it. Still
  distroless — no shell, no package manager, `nonroot`. Cost of a working Stage 2 is ~29MB of glibc.
- The Helm chart exposes `service.type` (was hardcoded `ClusterIP`), so the app is reachable on a
  cluster with no ingress controller without editing the rendered Service.
- The kind e2e suite now runs when the Dockerfiles or image pins change — the gap that let the
  Stage 2 break reach a release.
- `github.com/moby/spdystream` and `github.com/moby/go-archive` bumped (test-only dependencies).

No migrations, no configuration changes. The image is the whole point of the release. Six

## v0.0.2

### Shipped

- **Tenant identity is set by an application administrator.** An org carries a `tenant_id` — the
  value injected downstream as `X-Scope-OrgID` — assigned at org creation or once afterwards, and
  visible in the admin UI. It replaces caller-supplied tenancy, which would have let an org
  administrator mint a route naming a *different* org's tenant. One tenant belongs to one org, and
  it cannot be changed once set: routes already issued would keep routing while naming the wrong
  tenant.
- **Beacon, on by default.** Every claimed collector is served a small baseline pipeline that
  reports which components it is running and whether they are healthy. Component names and health
  only — never config text, never raw samples, and the projection type has no field a sample value
  could occupy. Ingest is authenticated with the agent's existing credential, body-size capped,
  rate limited per token, and expires from inventory when a collector stops reporting. Set
  `config.server.beacon_disabled: true` to turn it off entirely; nothing is mounted and no baseline
  is served.
- **Role enforcement now covers the live agent path.** A pipeline whose signals contradict its
  target collector's role is excluded from the served config on *both* paths that produce it —
  previously only the write-time recompute enforced it, so a collector polling inside the dirty
  window could be served a mismatch.
- **Destination templates with tenant bindings.** One platform-owned destination and credential,
  with per-team bindings that vary only the tenant. A binding has no column a credential could be
  written to, and the API refuses one that tries.

### RPC only — no UI yet

- Tenant route records (create, rotate, revoke). Nothing applies them to a cluster yet.
- Teams keyed by IdP group, pipeline ownership, and scoped write for team members.
- Service accounts with `propose` / `apply` capability. A machine write must name the human it acts
  for, and that claim is verified against the credential's own record of who created it. Every
  mutating procedure is checked individually rather than at one shared chokepoint.
- Audit records both halves of a delegated action, and an agent's proposal is now recorded.

### Built, not wired — do not plan against these yet

- Gateway API route rendering and in-cluster attachment verification (gate R1 unsigned).
- Receiver tier, including OTLP pass-through tenancy (R3 unsigned; must not default on before it).
- Three-way reconciliation of declared vs served vs observed collector state.
- Onboarding artifacts for connecting an application.
- k8s-monitoring chart-values generator.
- Grafana outcome verification — "did the data actually arrive".
- MCP agent interface, read-plus-propose. **Not in the release archives**; build from source. Its
  review gate (R6) is open.

### Fixed

- Pass-through tenancy did not preserve the tenant header through the batch processor, so every
  tenant would have shipped untagged. Found before anything shipped it.
- A machine actor's on-behalf-of claim was recorded in the audit log without being verified,
  letting a credential attribute a write to any human it named.
- The Grafana client leaked its token when a dereferenced value was formatted with `%+v`.
- Beacon ingest could be made to allocate a large buffer from a small request body: `snappy`
  allocates the length declared in the payload's own header before validating it.

### Upgrading from v0.0.1

Migrations `0008`–`0013` apply in order; run them as usual. Nothing requires new configuration.
